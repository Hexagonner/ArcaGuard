# 구조

Phase 0 실행 경로: `src/main.js` → `src/ui/testPanel.js` → Shadow DOM 테스트 패널.
스타일은 CSS inline import로 번들에 포함해 Shadow DOM 내부에 삽입한다.
`src/core/phase.js`는 현재 단계의 표시 상태이며 저장 설정이나 관리 정책 구현이 아니다.

사용자 승인 UI 보완: `ui/adminPage.js`는 사이트 안의 전체 화면 설정을 구성하고
`testPanel.js`가 표시/고정 상태와 포커스/단축키를 연결한다. 별도 서버/사이트 관리 경로를 만들지 않는다.
`adapters/runtime/uiPreferences.js`가 표시/고정의 버전 값을 검증하고,
`positionStore.js`의 기존 좌표 값과 별도로 보관한다.
`userscriptMenu.js`는 vite-plugin-monkey client로 개발 sandbox/배포 API를 연결하고,
`adminMenu.js`의 주입 가능한 메뉴 등록을 사용한다. UI 단위 테스트는 실제 GM API를 로드하지 않는다.
전용 설정 화면은 사용자 요청에만 열리고 숨김 상태에서도 단축키/메뉴로 접근할 수 있다.
이는 Phase 5의 채널/주제/신고/조치 설정 구현과 별개다.

- `core`: 공통 타입/오류/이벤트 (필요한 단계에서 추가).
- `detection`: 순수 광고 분석. 사이트 DOM/권한과 독립.
- `application`: 신고 처리/판정/조치 워크플로 조합.
- `adapters/arcalive`: 검증된 사이트 읽기/권한/관리 기능 경계.
- `adapters/runtime`: GM 저장/알림 API 경계.
- `storage`: 버전 설정/마이그레이션/기록.
- `ui`: 한국어 인터페이스.
- `utils`: 공통 유틸리티.
- `tests`: unit/integration/fixtures/manual.

Phase 0에서 쓰지 않는 계층은 `.gitkeep`으로 디렉터리만 보존한다.
향후 광고 분석 모듈의 공통 계약은 REQUIREMENTS.md 4.2를 따른다.
검증되지 않은 사이트 선택자, 관리자 API, 가짜 성공 응답은 만들지 않는다.
테스트는 별도 `vitest.config.js`로 빌드 플러그인과 격리한다.

## 향후 운영 계약의 계층 배치 (미구현)

세부 기준은 `OPERATING_REQUIREMENTS.md`에 둔다. 이 절은 구현된 모듈 목록이 아니다.

Phase 1 사용자 제공 근거에 따른 읽기 흐름은 신고 목록과 상세의 두 단계다.
목록의 신고 대상/작성자/신고자/표시 상태를 구별하고 상세에서 사유를 읽어 대상·신고 행과 결합한다.
사이트가 동일 계정의 반복 신고를 제한하므로 사이트 현재 총수와 사유를 읽고 별도 신고자 집계 장부를 만들지 않는다.
`tests/fixtures/arcalive/report-row.user-provided.json`은 합성 값의 전사 계약이며 실제 사이트 파서 입력/검증 HTML이 아니다.

REF-09~12의 후속 설계는 페이지 맥락/읽기 유효성과 권한을 분리한다. 사이트 어댑터는
목록/상세/게시글/편집의 채널·대상·필수 필드를 검증하고, 관측 영역/수명을 제한하며 노드 교체 시 재평가한다.
단발 loaded 플래그, 로그인/구독 표시, 색/취소선을 권한·서버 처리 상태로 해석하지 않는다.
application의 조회 스케줄러는 동일 채널의 진행 중 조회를 중첩하지 않고 반복 신호를 제한된 재대조로 합친다.
storage의 가져오기와 탭 간 신호는 허용 스키마/채널/버전 검증을 거치며 메시지를 관리 액션으로 직접 실행하지 않는다.
현재 인스턴스의 중지는 지연 저장과 독립하고 작업은 실행 직전 버전을 재확인한다.
설정 적용을 위해 사용자 작성 페이지를 자동 새로고침하지 않는다. 이 계약에 해당하는 운영 모듈은 아직 구현하지 않았다.

추가 사용자 근거에 따라 사이트 신고 알림은 상세 읽기 후보를 발생시키는 입력으로 분리한다.
알림 이벤트/대상 작업의 중복 실행은 방지하되 신고자별 기여 중복 키/장부는 만들지 않는다.
알림 상세 링크를 검증하고 읽기 큐→상세 사유 결합→기존 신고 검증/분석으로 연결할 계획이며
현재 화면의 알림 클릭/페이지 전환/읽음 처리를 읽기 흐름에 사용하지 않는다.
신고 처리 제출은 OP-11의 별도 쓰기 경계이며 읽기/글 이동에 암묵적으로 포함하지 않는다.
사이트 알림이 없거나 불완전해도 허용된 신고 목록 대조 경로가 필요하다. 읽음 처리 부작용과
알림 DOM/전달 방식은 직접 미검증이며 `report-detail.user-provided.json`은 합성 전사 계약일 뿐이다.

- 사이트 어댑터: 검증된 신고 링크/신고자 이름/사이트 총수/사유와 현재 글머리/상태를 읽는다.
  확인 불가 필드는 미검증으로 반환하고 임의 값이나 URL/계정 ID를 만들지 않는다.
- application: 신고 입력 검증 후 사이트 현재 총수/사유 스냅샷, 주제별 신고 호출 조건(광고 기본값 `광고`) 검사,
  OP-10 정책 분기와 최신 글머리 재조회/외부 이동 건너뛰기를 조합한다. 신고 내용은 광고 점수에 전달하지 않는다.
- storage: 채널/대상/신고 스냅샷과 작업·처리 상태를 분리한다. 신고자 중복 기여 장부는 만들지 않는다. 로그 보관 한도와 독립해
  안전하게 재구성할 수 있어야 한다. 로컬 저장소는 서로 다른 PC의 잠금이 아니다.
- ui: 이름/신고 내용 검토, 사이트 총수/호출어 포함 수와 검증 상태, 이미 처리/외부 이동 사유를 구별한다.
- detection: 광고와 비광고 주제별 근거/예외/점수를 평가하되 신고 내용은 어느 주제의 근거에도 가산하지 않는다.
- 주제 정책 계약은 `TOPIC_POLICIES.md`를 따른다. 사이트 어댑터가 링크 href/표시 이미지 URL/
  이미지와 링크의 관계를 출처별 자료로 반환하고 탐지 엔진은 DOM 없이 이 자료를 검사한다.
- 이미지 링크 수집은 DOM 읽기이며 OCR/QR 모듈과 독립이다. 수집 중 목적지 방문/클릭/동적 코드 실행은 하지 않는다.
- application은 예외/주제별 조건과 최종 대상 충돌을 확인해 단일 조치 또는 검토를 선택한다.
  같은 근거를 여러 주제 점수로 더하거나 topicId별로 글을 여러 번 이동시키지 않는다.

채널과 이동 대상은 사용자가 정하는 채널별 설정이다. prlvate→TEST는 개발 테스트 예시이며,
초기 자동 등록값/전역 선택자/이동 ID로 하드코딩하지 않는다. 작업은 설정 버전을 함께 확인하여
대기 중 채널/대상이 바뀐 경우 이전 설정으로 이동하지 않고 취소 또는 재검토해야 한다.

## 향후 조치 정책 분기 (설계 / 미구현)

- 설정의 `actionPolicy`는 REPORT_THRESHOLD 또는 AI_CONFIRMED 중 하나이고 `executionMode`와 독립이다.
  N은 현재 사이트 총수, K는 호출어 포함 사유 수다. 저장/마이그레이션/상속 시 검증하고
  정책 미지정/손상으로 자동 실행되거나 암묵적으로 신고 기준 정책이 선택되지 않게 한다.
- application은 유효한 신고/최신 상태/공통 예외를 확인한 뒤 정책 자격을 계산한다.
  REPORT_THRESHOLD는 총수 >= N 및 호출 사유 수 >= K로 자격을 반환하며 광고 분류기를 필수 호출하지 않는다.
  AI_CONFIRMED는 총수 >= N 및 현재 내용 지문에 묶인 유효한 로컬 AI 광고 결과를 요구한다.
  AI 정책에서 호출어는 필수가 아니며 실패/판단 불가/미준비를 다른 정책으로 대체하지 않는다.
- 두 분기는 조치 어댑터 앞에서 합류해 권한/현재 수/예외/기처리/정책 버전/긴급 중지를 재검증한다.
  정책 자격은 쓰기 성공이 아니다. Simulation/검토는 쓰기를 호출하지 않으며 자동 실행만 검증된 배경 경로를 사용한다.
- 작업은 채널/글/내용 지문/설정 버전/정책 및 필요한 모델 버전을 가진다.
  정책/조건 변경 시 미전송 작업을 취소/재평가하고 변경 전 AI 결과를 재사용하지 않는다.
  기록은 `신고 조건 충족`과 `AI 광고 판정`을 구별하며 탐지 점수와 신고 수를 합치지 않는다.

## 백그라운드 실행 계약 (미구현)

- 신고의 처리 카테고리·버튼·답변과 글 이동 대상·결과는 별도 계약이다(OP-11).
  설정은 채널별 신고 처리 OFF/작성자 통지 OFF를 기본으로 하고 버튼 ID/표시 이름/실제 효과를 독립 검증한다.
  카테고리/버튼 이름 변경·효과 변경은 재확인 대상이며 임의 CSS/코드/엔드포인트를 설정으로 실행하지 않는다.
- 미래 application은 기본적으로 글 이동 검증 후 활성화된 신고 처리 제출을 이어서 실행한다.
  사이트 어댑터의 신고 제출과 결과 읽기를 글 이동 인터페이스에서 분리하고 두 쓰기를 각각 Mock으로 검증한다.
  글 작업은 채널/글, 신고 제출 작업은 채널/신고 코드로 식별하며 신고자 집계 키로 사용하지 않는다.
- 저장은 articleMoveState와 reportResolutionState를 분리한다. 신고 완료는 글 이동 성공이 아니며
  이동 성공/신고 실패는 부분 완료다. 시간 초과는 재조회 전 재전송하지 않고 다른 관리자의 답변을 덮어쓰지 않는다.
  외부에서 신고만 완료됐는데 글 이동은 미확인이면 충돌 검토로 남긴다.
- `application`은 제한된 비동기 큐/백오프/취소 상태로 감시와 처리를 조합한다.
  브라우저 탭 비활성화/정지 후 재개에는 최신 자료를 다시 읽고 채널 쓰기를 직렬화한다.
- 사이트 어댑터의 쓰기는 검증된 백그라운드 요청으로만 실행하고 결과를 별도 읽기로 확인한다.
  현재 문서 내 관리 버튼 클릭/페이지 이동/새 탭/새로고침을 자동 실행 대안으로 제공하지 않는다.
  검증된 요청 방식이 없으면 검토 대기로 반환한다.
- 읽기 어댑터는 응답 해석과 리소스 로딩을 분리한다. 분리된 HTML 문서도 이미지/프레임 요청을
  발생시킬 수 있으므로 파싱 중 추가 네트워크 요청이 없는 방식을 검증한다.
  원문을 활성 DOM/숨겨진 프레임에 넣거나 링크를 따라가서 분석하지 않는다.
- UI는 처리 경로의 필수 단계가 아니며 로그/조용한 상태 표시만 갱신한다.
  포커스/스크롤/작성 내용/IME/목록 배치를 바꾸지 않고 알림 링크는 명시적 클릭에만 반응한다.
- 무거운 분석은 Worker/분할 실행/작업 한도를 적용하고 자원 부족 시 처리량을 줄인다.
  Workers가 브라우저 종료 후 독립 상주하는 서비스인 것처럼 설명하지 않는다.
- 상세 경계/알림 기본값/실행 한계는 `OPERATING_REQUIREMENTS.md` OP-07을 따른다.
