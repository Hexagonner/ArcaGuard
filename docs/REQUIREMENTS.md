# ArcaGuard — Codex 개발 통합 명세서

**프로젝트 버전:** Specification 1.3 — 백그라운드 처리·관리자 사용 방해 금지 보완 (2026-10-24)  
**프로젝트명:** ArcaGuard  
**프로그램 유형:** Tampermonkey Userscript  
**개발 언어:** JavaScript (ES Modules)  
**개발 도구:** Node.js, Vite, vite-plugin-monkey, Vitest, ESLint  
**운영 환경:** 아카라이브(arca.live)  
**개발 방식:** Codex를 이용한 단계별 구현  
**최우선 조건:** 무료 운영, 안정성, 범용성, 사용자 설정 가능성

변경 기준: 사용자가 지정한 테스트 채널/대상 탭, 복수 관리자 및 신고자 중복 집계 방지.
운영 채널과 대상 탭은 사용자가 채널별로 자유롭게 선택/변경하며 테스트 값은 고정 기본값이 아니다.
세부 계약과 인수 조건은 [운영 요구사항](OPERATING_REQUIREMENTS.md)을 따른다.
광고 외 주제 추가, 주제별 예외와 이미지에 걸린 링크 검사는 [주제 정책](TOPIC_POLICIES.md)을 따른다.
광고 글의 탭 이동은 백그라운드에서 수행하고 관리자 화면/입력/포커스를 방해하지 않아야 한다.
조용한 알림 기본값과 실행 한계는 [운영 요구사항 OP-07](OPERATING_REQUIREMENTS.md#op-07-백그라운드-처리와-사용-방해-금지)을 따른다.
사이트의 새 신고 알림을 백그라운드 검토 후보의 입력으로 활용하는 계약은 운영 요구사항 OP-09를 따른다.
사이트가 계정별 동일 대상 신고를 1회로 제한한다는 사용자 확인에 따라 총 신고 수는 사이트 값을 사용한다.
별도 신고자 중복 집계는 만들지 않고 재조회/중복 알림/기처리 대상의 재실행 방지만 유지한다 (OP-03).
사용자가 이번 설명의 ‘삭제’를 지정 탭 이동으로 명확히 했으며 자동 삭제/계정 차단 금지는 유지한다.
초기 원문은 [Specification 1.0](archive/SPECIFICATION_1.0.md)에 보존했다.
이 개정은 요구사항 보완이며 Phase 1~9 구현이나 실제 게시글 이동 승인이 아니다.

# 0. Codex 최초 실행 지시

당신은 ArcaGuard 프로젝트의 수석 소프트웨어 엔지니어다.

이 명세서를 프로젝트의 최상위 요구사항으로 사용하여 Tampermonkey 기반 아카라이브 광고 관리 자동화 프로그램을 개발한다.

다음 원칙을 반드시 준수한다.

1. 실제로 동작하는 소프트웨어를 단계별로 구현한다.
2. 구현되지 않은 기능을 구현되었다고 보고하지 않는다.
3. 기존 프로젝트가 존재하면 먼저 조사하고 가능한 한 보존한다.
4. 저장소 루트에 `AGENTS.md`를 생성하여 개발 지침을 유지한다.
5. 세부 구현 계획은 `docs/PLAN.md`에 작성한다.
6. 사이트 구조를 추측하여 관리자 기능을 구현하지 않는다.
7. 공개된 소스코드, 공식 문서, 실제 DOM 및 검증된 동작을 근거로 개발한다.
8. 테스트는 가능한 한 자동화한다.
9. 실제 게시글을 수정하는 기능은 명시적인 승인과 검증 이전에 실행하지 않는다.
10. 유료 AI API, 유료 클라우드, 별도 서버를 필수로 사용하지 않는다.
11. 자동 삭제와 계정 차단 기능을 구현하지 않는다.
12. 단계별 완료 보고서를 작성한다.
13. 현재 승인된 Phase만 구현하고 완료 시 중단한다.

최초 작업은 **Phase 0: 프로젝트 기반 구축**으로 제한한다.

# 1. 프로젝트의 목적

## 1.1 해결하려는 문제

아카라이브 커뮤니티에는 다양한 형태의 무허가 광고 게시물이 작성될 수 있다.

광고는 다음과 같은 방식으로 나타난다.

- 일반적인 광고 문구
- 외부 URL이 포함된 게시물
- URL 없이 특정 검색어를 찾도록 유도하는 광고
- 투자 수익 인증이나 후기 형태로 위장한 광고
- 이미지 안에 URL이나 광고 문구를 넣은 게시물
- QR코드를 포함한 광고
- 댓글에 작성되는 광고
- 공백, 숫자, 특수문자 등을 삽입한 광고
- 한글 철자나 자모를 변형한 광고
- 문맥을 이용해 광고임을 숨기는 우회 광고

채널 관리자는 이러한 게시물을 직접 확인하고 삭제하거나 작성자를 차단할 수 있지만, 신고가 많아질수록 처리 부담이 커진다.

ArcaGuard는 신고된 게시글을 자동 분석하고, 광고로 판단된 게시물을 관리자가 지정한 글머리로 이동시켜 관리 부담을 줄이는 시스템이다.

광고는 기본 사용 사례이며 리딩방/쇼핑몰 링크 같은 세부 주제와 광고 외 사용자 정의 주제를 지원한다.
사용자가 주제별 규칙/예외/처리 방식을 설정하고 검토 또는 글머리 이동에 사용한다.
이후의 광고 중심 예시는 광고 주제의 기본 흐름이며 비광고 결과는 해당 주제명으로 표시한다.

## 1.2 핵심 목표

- 일반 이용자가 신고를 통해 봇을 호출할 수 있어야 한다.
- 최소 신고 개수는 관리자가 설정할 수 있어야 한다.
- 광고 여부를 정규 표현식과 문자열 분석으로 판단해야 한다.
- 의도적으로 변형된 광고 문구도 탐지해야 한다.
- 이미지에 적힌 광고 문구도 분석할 수 있어야 한다.
- 무료 로컬 AI를 선택적으로 사용할 수 있어야 한다.
- AI 사용 여부와 민감도를 설정할 수 있어야 한다.
- 분석 결과가 기준을 충족하면 지정된 글머리로 이동시킬 수 있어야 한다.
- 모든 관리 작업은 해당 채널의 권한을 검증한 뒤 실행해야 한다.
- 관리자에게 처리 결과를 알리고 판단 근거를 제공해야 한다.
- 여러 채널에서 서로 다른 설정으로 사용할 수 있어야 한다.
- 광고/비광고 주제를 사용자가 추가·수정·삭제하고 주제별 탐지 규칙과 예외를 정할 수 있어야 한다.
- 이미지 파일 주소와 이미지에 걸린 실제 클릭 목적지를 구별하여 검사해야 한다.

## 1.3 구현하지 않을 기능

다음 기능은 ArcaGuard의 범위에서 제외한다.

- 게시글 자동 삭제
- 계정 자동 차단
- 댓글 자동 삭제
- 관리자 권한 우회
- 신고 수나 신고 내용 조작
- 플랫폼의 인증 절차 우회
- 사이트에 존재하지 않는 관리자 권한 생성
- 유료 AI API를 필수로 요구하는 기능
- 관리자 PC가 꺼져 있어도 동작한다고 보장하는 24시간 감시 기능
- 광고로 판단했다는 이유만으로 이용자를 자동 제재하는 기능

글머리 이동 역시 실제 게시물의 노출 상태에 영향을 주는 관리 조치이므로 별도의 안전장치를 적용한다.

# 2. 전체 시스템 동작

## 2.1 기본 처리 과정

1. 일반 이용자가 광고로 의심되는 게시글을 발견한다.
2. 해당 게시글을 신고한다.
3. 신고 사유에 키워드 `광고`를 포함한다 (`광고)`도 일치한다).
4. ArcaGuard가 관리자의 신고 목록을 확인한다.
5. 신고 대상 링크, 사이트가 제공한 신고자 이름/계정 식별값, 신고 내용을 검증한다.
6. 동일 대상을 신고한 사용자별로 중복 제거한 전체/호출 신고 수가 임계값 이상인지 확인한다.
7. 해당 채널의 관리자 권한을 확인한다.
8. 신고 대상 게시글의 제목과 본문을 가져온다.
9. 외부 URL, 이미지, QR코드 등의 정보를 수집한다.
10. 설정에 따라 정규식 및 우회 문자 분석을 실행한다.
11. OCR이 활성화되어 있으면 이미지에서 글자를 추출한다.
12. 로컬 AI가 활성화되어 있으면 문맥을 분석한다.
13. 각 분석 결과를 종합해 광고 위험도를 평가한다.
14. 설정된 자동 이동 조건을 확인한다.
15. 최신 상태를 다시 읽어 이미 처리되었거나 다른 관리자가 이동한 글을 건너뛰고,
    모든 조건을 충족한 미처리 글만 지정된 글머리로 이동시킨다.
16. 실제 글머리 변경 성공 여부를 확인한다.
17. 관리자에게 알림을 보낸다.
18. 처리 결과와 판단 근거를 기록한다.

## 2.2 광고 신고 호출 방식

기본 신고 호출어는 다음과 같다.

`광고`

신고 **내용**에 이 문자열이 포함되는지를 검사한다. `광고)`, `광고 의심`,
`이미지 광고 신고`는 모두 후보가 된다. 글 제목/신고자 이름/링크에만 있는 `광고`는
호출로 계산하지 않는다. 이 변경은 앞으로 구현할 새 기본값이며 저장된 설정은 현재 없다.

신고 예시:

- `광고) 텔레그램 홍보`
- `광고) 외부 사이트 가입 유도`
- `광고) 사진에 광고가 들어있음`

관리자는 호출어를 자유롭게 변경할 수 있어야 한다.

호출어의 일치 방식은 다음 중 선택할 수 있도록 설계한다.

- 완전 일치
- 부분 문자열 일치
- 안전한 정규식 일치

기본값은 부분 문자열 일치다.

호출어는 신고를 분석 대상으로 선정하는 목적으로만 사용한다.

신고자가 작성한 `광고`라는 단어 자체는 게시글이 광고라는 증거로 계산하지 않는다.
`광고가 아닌 것 같습니다`처럼 키워드가 들어간 내용도 분석 후보일 뿐 광고 확정이 아니다.

## 2.3 신고 임계값

기본값은 **사이트 총 신고 수 1건 이상**이다. 같은 사용자가 동일 대상을 한 번만 신고할 수 있음이
사용자에 의해 확인됐으므로 별도 신고자 고유 집계/기여 장부를 구현하지 않는다.

두 조건을 구분한다.

- 사이트가 현재 표시하는 총 신고 수가 최소 개수 이상이어야 한다.
- 현재 확인한 신고 사유 중 키워드 포함 건수가 호출 임계값 이상이어야 한다.

향후 설정에서 호출어가 포함된 신고만 몇 건 이상 필요한지도 별도로 지정할 수 있게 한다.

신고 수 또는 신고 사유를 읽을 수 없는 경우 임의로 값을 추정하지 않는다.

신고 데이터가 확인되지 않으면 자동 이동을 실행하지 않는다.

신고자 이름은 신고 행의 사이트 제공 필드에서 확인한다. 안정적 계정 ID가 없다는 이유만으로
사이트 총수를 다시 계산하거나 사용할 수 없다고 판단하지 않는다. 임의 ID/로컬 신고자 장부는 만들지 않는다.
새로고침/재수집/다중 탭 조회는 최신 값으로 교체하고 이전 수에 더하지 않는다.
총수/대상/사유 읽기 범위가 불명확하면 미확인으로 남기며 사이트의 신고 제한을 다시 구현하지 않는다.
중복 알림/동일 작업 실행과 기처리 글 재이동은 계속 방지한다. OP-03/OP-04를 따른다.

## 2.4 댓글 신고

댓글과 게시글은 구별한다.

광고 댓글이 신고되었다는 이유로 정상적인 부모 게시글을 자동 이동시켜서는 안 된다.

댓글 신고는 광고 분석 후 관리자 검토 목록에 추가하고, 해당 댓글로 이동할 수 있는 링크를 제공한다.

댓글 삭제는 관리자가 직접 수행한다.

# 3. 핵심 기능 요구사항

## FR-01. 채널 관리

ArcaGuard는 복수의 아카라이브 채널을 지원한다.

각 채널의 설정은 독립적으로 저장한다.

사용자는 코드 수정 없이 설정 화면에서 채널을 추가/변경/삭제하고 채널마다 이동 대상 탭을
선택/변경할 수 있어야 한다. 특정 테스트 채널이나 탭으로 제한하지 않는다.
최초 실행의 등록 채널과 이동 대상은 미설정이며 사용자 선택 후 실제 존재/권한을 검증한다.

관리자가 설정할 수 있는 항목:

- 채널 주소
- 채널 ID
- 감시 활성화 여부
- 관리자 권한 검증 상태
- 신고 호출어
- 신고 수 임계값
- 확인 주기
- 광고 탐지 규칙
- 정규화 방식
- 한글 유사도 설정
- 이미지 OCR 설정
- AI 사용 여부
- AI 판단 민감도
- 광고 이동 임계값
- 이동 대상 글머리
- 알림 방식
- 자동 이동 활성화 여부

한 채널에서 변경한 설정은 다른 채널에 영향을 주지 않아야 한다.

## FR-02. 관리자 권한 확인

사용자가 채널을 등록하면 해당 채널에 대한 관리자 권한을 확인한다.

필요한 기능:

- 로그인 상태 확인
- 채널 식별
- 관리자 전용 메뉴 확인
- 신고 목록 접근 권한 확인
- 글머리 변경 권한 확인

권한 상태는 다음과 같이 구분한다.

- `unverified`
- `verified`
- `failed`
- `unsupported`

관리자 메뉴의 존재만으로 글머리 변경 권한까지 확인한 것으로 간주하지 않는다.

실제 기능 검증을 통해 권한을 확인한다.

권한 검증에 실패하면 자동 이동 기능을 비활성화한다.

비밀번호, 세션 쿠키, 인증 토큰을 자체 저장하지 않는다.

기존 브라우저의 인증 상태와 사이트의 정상적인 권한 검사를 이용한다.

## FR-03. 신고 모니터링

관리자에게 제공되는 신고 목록을 주기적으로 검사한다.

설정할 수 있는 파라미터:

- 모니터링 활성화
- 신고 호출어
- 최소 전체 신고 수
- 최소 호출 신고 수
- 모니터링 간격
- 한 번에 검사할 최대 신고 수
- 중복 검사 방지
- 오류 발생 시 재시도 간격

기본 모니터링 간격은 120초로 한다.

설정 가능 범위는 사이트 부하와 브라우저 실행 제약을 고려하여 정한다.

감시 기능은 Tampermonkey 스크립트가 활성화된 페이지에서 실행되는 구조를 기본으로 한다.

브라우저가 종료되었거나 실행 페이지가 없는 상태에서 감시를 보장하지 않는다.

실제 신고 목록과 신고 사유의 접근 방식은 반드시 별도로 검증한다.

신고 대상 링크/대상 유형/신고자 표시 이름/사이트 총 신고 수/신고 내용/키워드 판정/
데이터 검증 상태를 분리해 읽는다. 외부 호스트, 다른 채널, 불명확한 댓글 링크,
필수 필드 누락은 자동 처리하지 않는다. 사이트 총수와 호출어 포함 사유 수를 구별해 표시한다.

## FR-04. 정규 표현식 광고 탐지

JavaScript `RegExp`를 기반으로 광고 문구를 분석한다.
같은 규칙 엔진을 사용자 정의 주제에도 적용하되 주제별 결과/근거/예외를 구별한다.

관리자가 규칙을 직접 추가·수정·삭제할 수 있어야 한다.

각 규칙의 속성:

- 규칙 ID
- 규칙 이름
- 정규식 패턴
- Flags
- 설명
- 활성화 여부
- 주제별 점수 가중치
- 적용할 텍스트 형태
- 탐지 범주
- 제외 조건
- 테스트 결과

예시 탐지 범주:

- 외부 투자방 가입 유도
- 텔레그램·오픈채팅 유도
- 금융 수익 보장
- 외부 사이트 홍보
- 포털 검색 유도
- 연락처 및 상담 유도
- 반복적인 홍보 문구

정규식 엔진은 원본 문자열과 정규화 문자열을 선택적으로 검사할 수 있어야 한다.

잘못된 정규식은 저장 전에 감지한다.

복잡한 정규식이 브라우저를 멈추지 않도록 Worker 기반 실행 제한 또는 이에 준하는 안전한 검사 방식을 구현한다.

임의의 정규식을 메인 스레드에서 무제한 실행해서는 안 된다.

## FR-05. 광고 우회 문자 탐지

이 기능은 필수 핵심 기능이다.

일반적인 정규식만으로 감지하기 어려운 광고 문구 변형을 처리한다.

### A. 공백·숫자·특수문자 삽입

다음과 같은 사례를 탐지 대상으로 삼는다.

- `대출권유`
- `대 출 권 유`
- `대.출.권.유`
- `대@414출@$15권@$5유`

구현 방식:

- 유니코드 정규화
- 특수문자 제거
- 공백 제거
- 숫자 삽입 패턴 검사
- 문자 사이의 노이즈 허용
- 제한된 구간의 정규식 유사 매칭

숫자와 특수문자를 무조건 제거해서 전체 문장을 합치는 방식만 사용해서는 안 된다.

정상 문장이 우연히 광고 키워드와 합쳐지는 오탐을 방지해야 한다.

검사 대상 문자 간 거리와 노이즈 길이를 제한한다.

### B. 한글 자모 변형

다음 표현을 탐지 대상으로 삼는다.

- `대출권유`
- `떄출꿘유`

구현 방식:

1. 한글 음절을 초성·중성·종성으로 분해한다.
2. 표준 키워드의 자모와 비교한다.
3. 유사 자모 치환 비용을 계산한다.
4. 문자열 유사도를 측정한다.
5. 설정된 임계값 이상이면 광고 의심 후보로 등록한다.

단순한 NFKC 정규화만으로 다른 한글 음절이 동일해지는 것은 아니므로, 별도의 한글 자모 분석을 구현한다.

### C. 문자열 유사도

가중 편집 거리 또는 이에 준하는 문자열 유사도 알고리즘을 사용한다.

다음 차이를 별도로 평가한다.

- 자음 변경
- 모음 변경
- 된소리·예사소리 변경
- 글자 삽입
- 글자 삭제
- 글자 순서 변경
- 숫자·특수문자 삽입

관리자가 유사도 임계값을 설정할 수 있어야 한다.

기본 정책:

- 정확히 일치하는 키워드: 강한 근거
- 숫자·특수문자 삽입형: 중간 이상 근거
- 한글 유사도 일치: 보조 근거
- 문맥 없이 유사도만 높은 경우: 자동 이동 금지

### D. 성능 제한

모든 단어를 모든 광고 키워드와 무제한 비교하지 않는다.

후보 문자열을 먼저 추출한 뒤 유사도를 계산한다.

문자열 길이, 비교 횟수, 최대 탐색 구간을 제한한다.

필요한 경우 사전 인덱스, 길이 필터, 초성 기반 후보 필터 등을 사용한다.

## FR-06. 이미지 문자 인식

무료 OCR 엔진으로 이미지의 문자를 분석한다.

우선 검토 기술은 Tesseract.js다.

기능:

- 게시글 이미지 탐색
- 이미지 크기 확인
- 한국어 문자 인식
- 영어 문자 인식
- 숫자·URL 문자 인식
- OCR 결과 정규화
- 광고 탐지 엔진과 연동
- 이미지 분석 결과 캐시

관리자가 설정할 수 있는 항목:

- OCR ON/OFF
- 최대 분석 이미지 수
- 최대 이미지 크기
- 처리 제한 시간
- OCR 언어
- 이미지 분석 실패 시 정책

게시글의 이미지가 광고라는 판단은 문자 인식 결과와 광고 유도 문맥을 결합한다.

이미지가 포함되었다는 이유만으로 광고로 판단하지 않는다.

QR코드 분석은 OCR과 별도 모듈로 설계한다.

사진에 걸린 하이퍼링크는 픽셀 분석이 아닌 별도의 DOM 수집으로 처리한다.
OCR/QR이 OFF여도 실제 이미지 링크 목적지를 수집/검사할 수 있어야 한다 (FR-14).

CORS, CSP 및 Tampermonkey 실행 환경 제약을 확인하고, 허용된 방법으로 접근 가능한 이미지에 대해서만 분석한다.

## FR-07. 무료 로컬 AI

AI는 선택 기능이다.

유료 API는 사용하지 않는다.

우선 후보 기술은 Transformers.js 기반 브라우저 로컬 추론이다.

AI 모델은 실제 한국어 광고 분류 성능과 브라우저 호환성이 검증된 경우에만 연결한다.

설정 기능:

- AI 활성화 토글
- 모델 선택
- 모델 설치 여부 표시
- 모델 크기 표시
- AI 분석 민감도
- 모델 실행 제한 시간
- 정규식과 AI 결과 결합 방식
- AI 오류 처리 방식

AI는 다음과 같은 상황에서 활용한다.

- 직접적인 광고 문구가 없는 경우
- 검색어를 이용한 우회 광고
- 후기 형태의 광고
- 광고 문구와 비판적인 인용을 구별해야 하는 경우
- 정규식 결과가 애매한 경우

AI를 사용하지 않더라도 시스템의 기본 기능은 정상 작동해야 한다.

모델 파일은 이용자의 브라우저 또는 PC에서 처리한다.

모델 다운로드가 필요하면 용량과 출처를 안내한다.

게시글 및 신고 내용을 외부 AI 서버로 자동 전송하지 않는다.

AI 분석 실패를 광고 확정으로 처리하지 않는다.

## FR-08. 광고 위험도 산출

광고 판정은 단순한 키워드 일치 여부가 아니라 복수의 근거를 종합하여 수행한다.

최종 점수는 0~100으로 정규화한다.

초기 규칙은 실험용이며, 실제 광고 사례를 이용해 보정한다.

광고 근거 범주:

- 직접적인 광고 표현
- 외부 서비스명
- 가입·검색·구매 유도
- 수익 보장 문구
- 확인된 광고 도메인
- OCR로 발견된 광고 표현
- 우회 문자 탐지
- AI 문맥 판정

정상 게시글로 판단할 근거도 고려한다.

예:

- 광고 피해 사례 설명
- 사기 광고 경고
- 광고 문구 인용
- 정상적인 투자 분석
- 기사나 공시 내용 인용

광고 근거를 설명할 수 있어야 한다.

점수는 통계적으로 검증된 확률이 아니므로 '광고일 확률 90%'처럼 표기하지 않는다.

대신 '광고 위험 점수 90점'으로 표시한다.

사용자 정의 비광고 주제는 주제별 점수와 근거로 표시하고 '광고'로 단정하지 않는다.
주제 간 점수 합산은 하지 않으며 같은 링크의 중복 발견을 독립 근거로 부풀리지 않는다.

## FR-09. 자동 이동 정책

자동 이동은 다음 조건을 모두 만족해야 한다.

아래 광고 조건은 다른 주제에는 '해당 주제 분석/점수/근거'로 적용한다.
추가로 주제 활성/예외의 자동 처리 금지 여부/정책 버전/복수 주제 대상 충돌을 확인한다.

- 감시 활성화
- 유효한 신고 존재
- 호출어 일치
- 신고자별 중복 제거 후 전체/호출 신고 임계값 충족
- 광고 분석 완료
- 광고 위험 점수 임계값 충족
- 독립적인 광고 근거 최소 개수 충족
- 관리자 권한 확인
- 대상 글머리 확인
- 현재 게시글 상태 및 다른 관리자의 처리 여부 확인
- 이미 처리된 글머리 아님, 분석 후 외부 이동 없음, 중복 처리 아님
- 자동 이동 모드 활성화
- 긴급 중지 상태 아님

기본 광고 점수 기준:

- 0~49점: 이동하지 않음
- 50~84점: 관리자 검토
- 85~100점: 자동 이동 후보

실제 자동 이동은 이 점수만으로 결정하지 않는다.

독립적인 광고 근거를 기본 2개 이상 요구한다.

광고 문구를 인용하거나 경고하는 게시글 등 문맥적으로 의심스러운 사례는 검토 대상으로 처리한다.

OCR이나 AI의 실패로 판정에 필요한 증거가 누락된 경우 자동 이동을 실행하지 않는다.

관리자는 자동 이동 기준 점수, 최소 증거 그룹 수, 수동 검토 조건을 변경할 수 있다.

## FR-10. 글머리 이동

사용자는 각 채널에서 이동할 대상 글머리를 지정한다.

현재 사용자가 지정한 테스트 범위는 **https://arca.live/b/prlvate**이며,
이 채널에서 광고 판정 조건을 충족한 미처리 글의 이동 대상 이름은 **TEST**다.
이는 개발 테스트용 선택 예시다. 일반 사용자는 다른 채널과 해당 채널의 다른 탭을 선택할 수 있다.
사용자는 이 채널의 관리자임을 밝혔다. 이는 사용자 제공 조건이며 실제 권한이나
TEST 탭의 존재/ID/이동 의미를 검증한 결과는 아니다.
채널 ID 표기는 `prlvate`를 그대로 사용하며 `private`로 교정하지 않는다.
TEST는 채널별 설정으로 등록할 대상 이름이며 전역 하드코딩하지 않는다.
실제 글머리 ID는 해당 채널의 검증된 목록에서 선택한다. 자동 이동 기본값은 계속 OFF다.
대상 선택/변경은 UI에서 지원하며 이름/ID를 코드에 입력할 필요가 없어야 한다.
채널/대상 설정이 변경되면 그 채널의 대기 작업을 취소 또는 재검토하고,
이동 직전에 설정 버전/대상/권한을 재확인한다. 과거 기처리 글을 새 대상에 자동 재이동하지 않는다.

예:

- 휴지통
- 광고격리
- 관리자검토
- 기타 관리자 전용 글머리

글머리 이름이나 ID는 하드코딩하지 않는다.

가능하다면 채널에서 실제 제공하는 글머리 목록을 읽어 선택하도록 한다.

다음 사항을 반드시 확인한다.

- 이동 대상이 실제 글머리인지
- 이동이 삭제와 별개의 동작인지
- 해당 관리자에게 이동 권한이 있는지
- 이동 요청이 정상적인 관리 기능인지
- 이동 완료 후 실제 글머리가 변경되었는지

휴지통 탭 이동이 플랫폼에서 실질적인 삭제 처리와 연결된다면 자동 이동 기능을 활성화하지 않고 재검토한다.

실제 관리자 UI 또는 확인된 공식 동작을 통해서만 변경한다.

임의의 비공개 API를 추측하여 요청하지 않는다.

## FR-11. 관리자 알림

자동 이동 성공은 처리 기록과 조용한 상태 표시로 확인할 수 있어야 한다.
기본값은 개별 성공 팝업/OS 알림/소리/패널 자동 열림 없이 처리 기록만 남기는 방식이다.
개별 알림은 사용자가 명시적으로 켠 경우에만 제공하고 반복 사건은 묶거나 빈도를 제한한다.
실패나 재인증 필요 상태도 팝업/화면 전환을 강제하지 않고 기록/상태 표시에 남긴다.

알림 내용:

- 채널명
- 게시글 제목
- 게시글 URL
- 신고 개수
- 신고 호출어
- 적용된 광고 탐지 규칙
- 광고 위험 점수
- 이동 전 글머리
- 이동 후 글머리
- 처리 시각
- 최종 처리 상태

관리자가 알림이나 기록의 링크를 직접 클릭했을 때만 관련 게시글을 열도록 한다.

알림 기능은 Tampermonkey에서 지원하는 API를 우선 사용한다.

알림이 차단된 경우 확장 프로그램 내부의 처리 기록에 남긴다.

## FR-12. 처리 기록

다음 데이터를 저장한다.

- 처리 식별자
- 게시글 ID
- 채널 ID
- 검사 시각
- 탐지 규칙
- 최종 점수
- 자동 이동 여부
- 이동 전 글머리
- 이동 후 글머리
- 성공·실패 여부
- 관리자 확인 여부

개인정보와 신고 원문은 필요한 범위에서만 보관한다.

보관 기간과 최대 저장 건수는 관리자가 설정할 수 있어야 한다.

기본 로그 보관 한도는 최근 1,000건으로 한다.

중복 제거에 필요한 신고자 식별 정보/신고 내용은 최소 범위로만 다루며 기본 로그나
내보내기에 원문/이름/계정 식별값을 무조건 복사하지 않는다. 테스트 Fixture는 합성 자료를 쓴다.
로그 삭제나 1,000건 한도 초과로 중복 방지 상태가 초기화되어 재처리되지 않아야 한다.
다른 관리자의 이동을 확인한 경우 자체 이동 성공과 구별해 `SKIPPED` 및 사유를 기록한다.

설정값 내보내기와 처리 로그 내보내기는 별도 기능으로 제공한다.

## FR-13. 사용자 정의 주제와 예외

사용자는 채널별로 리딩방/쇼핑몰 링크 등 광고 주제뿐 아니라 거래글/스포일러 등 다른 주제도
직접 추가·수정·삭제·활성화할 수 있어야 한다. 예시는 강제로 등록하지 않는다.
주제명만 등록한 상태는 규칙 없는 초안이며 자동 분류가 완성된 것으로 표시하지 않는다.

각 주제는 이름/설명/규칙/검사 출처/점수·근거 임계값/예외/신고 호출 조건/처리 방식/
채널 대상 상속 또는 주제별 대상 탭/설정 버전을 가진다. 자동 이동 기본값은 OFF다.
비광고 신고 호출어도 설정 가능하며 신고 내용은 판정 근거에 가산하지 않는다.

예외는 주제별 허용 키워드/URL/검증 가능한 작성자 등의 조건과 범위를 명시하고,
일치 시 규칙 근거 제외/해당 주제 자동 처리 제외/검토 전환 등의 효과를 구별한다.
한 주제의 예외가 다른 주제를 무조건 허용하지 않는다. 예외 오류/시간 초과 시 자동 조치를 중단한다.
주제·예외 변경 시 대기 작업을 재검토하고 기처리 글을 자동 재이동하지 않는다.
복수 주제의 이동 대상이 충돌하면 관리자 검토, 같으면 한 번만 조치한다.
자동 삭제/계정 차단은 주제 추가와 무관하게 계속 금지한다.

## FR-14. 이미지 하이퍼링크 검사

검증된 게시물 내용 영역에서 사진에 걸린 실제 링크 목적지를 읽어 주제별 URL 규칙과 예외에 적용한다.
이미지 src/currentSrc 등 파일 주소, 링크 href, OCR 문구, QR 주소를 분리해 출처와 근거를 남긴다.
상대 링크도 해석하되 외부 URL을 열거나 클릭/스크립트 실행으로 목적지를 알아내지 않는다.
확인 불가한 동적 링크는 `unsupported`/미확인으로 표시한다.

외부 링크/확대용 이미지 링크/외부 CDN 이미지가 있다는 사실만으로 광고를 확정하지 않는다.
이미지 링크 수집은 OCR/QR과 독립적으로 동작하며 후속 Phase 1/2/4에서 조사·Mock·연결하고,
Phase 6에서는 OCR/QR 자료를 추가한다. 상세 계약은 TOPIC_POLICIES.md를 따른다.

# 4. 광고 탐지 엔진 설계

## 4.1 다단계 처리 구조

광고 분석은 다음 순서로 실행한다.

**Stage 1 — 원본 수집**

제목, 본문, URL, 이미지 텍스트를 분리하여 수집한다.
일반 링크/이미지 링크의 실제 목적지와 이미지 파일 URL도 별도 출처로 수집한다.
이미지 링크 수집에는 OCR이 필요하지 않다.

**Stage 2 — 텍스트 정규화**

NFKC 정규화, 공백·특수문자 처리 및 한글 자모 분석용 데이터를 생성한다.

**Stage 3 — 정규식 검사**

원본 및 정규화된 텍스트를 규칙과 비교한다.

**Stage 4 — 우회 문자 검사**

숫자·특수문자 삽입 및 한글 유사도 기반 탐지를 실행한다.

**Stage 5 — 이미지 분석**

OCR 및 QR 분석이 켜져 있을 경우 이미지의 정보를 추출한다.

**Stage 6 — AI 문맥 분석**

AI 사용이 활성화된 경우에만 실행한다.

**Stage 7 — 광고 근거 통합**

동일한 근거가 반복 계산되지 않도록 결과를 그룹별로 통합한다.

**Stage 8 — 의사결정**

광고 위험 점수, 제외 근거, 관리자 권한, 신고 조건을 종합해 최종 처리 상태를 결정한다.

## 4.2 분석 결과 인터페이스

모든 광고 탐지 모듈은 공통 형태의 결과를 반환해야 한다.

필수 필드:

- `engine`: 탐지 엔진 이름
- `topicId`: 사용자 정의 주제 식별자
- `matched`: 탐지 여부
- `ruleId`: 규칙 식별자
- `evidenceGroup`: 증거 범주
- `score`: 기여 점수
- `source`: 제목, 본문, 일반 링크, 이미지 링크 목적지, 이미지 파일 URL, OCR, QR 등
- `evidenceId`: 같은 원천 근거의 중복 가산을 방지하는 식별값
- `appliedExceptions`: 적용된 예외와 범위/효과
- `matchedText`: 일치한 문자열
- `reason`: 사람이 이해할 수 있는 근거
- `status`: success, skipped, unsupported, error
- `error`: 오류 정보

광고 탐지 엔진은 사이트의 관리자 권한을 직접 사용하지 않는다.

## 4.3 우회 문자 탐지 예제

아래 사례를 반드시 단위 테스트에 포함한다.

| 입력 | 기대 처리 |
|---|---|
| `대출권유` | 기본 키워드 탐지 |
| `대 출 권 유` | 공백 우회 탐지 |
| `대.출.권.유` | 특수문자 우회 탐지 |
| `대@414출@$15권@$5유` | 숫자·특수문자 우회 탐지 |
| `떄출꿘유` | 한글 자모 유사도 후보 탐지 |
| `무료 급등주 추천방 입장` | 복수 광고 근거 탐지 |
| `네이버에 OO투자 검색하세요` | 외부 검색 유도 탐지 |
| `대출권유 광고를 조심하세요` | 광고 언급 및 경고 문맥 확인 |
| `광고 업체 신고 방법` | 키워드만으로 자동 이동 금지 |

이 테스트의 '탐지'와 '자동 이동'은 구별한다.

예를 들어 `떄출꿘유`가 유사 표현으로 탐지되어도 그것만으로 게시글을 자동 이동시키지 않는다.

# 7. 사용자 설정 시스템

## 7.1 설정 저장 방식

Tampermonkey의 저장 기능을 사용한다.

가능하면 `GM_getValue`, `GM_setValue` 등을 런타임 어댑터 내부에서 호출한다.

애플리케이션의 다른 계층이 Tampermonkey 전용 API에 직접 의존하지 않도록 한다.

설정 데이터에는 `schemaVersion`을 포함한다.

설정 마이그레이션 기능을 제공한다.

## 7.2 설정 항목 및 기본값

| 설정 | 기본값 |
|---|---|
| 프로그램 활성화 | ON |
| 감시 활성화 | OFF |
| 처리 모드 | Simulation |
| 신고 호출어 | `광고` (신고 내용의 부분 문자열) |
| 최소 전체 신고 수 | 사이트 총 신고 수 1건 |

# 9. 관리자 조치 안전장치

## 9.1 처리 상태

각 신고 대상에 다음 상태를 사용한다.

- `DISCOVERED`
- `REPORT_VERIFIED`
- `ARTICLE_FETCHED`
- `ANALYZING`
- `REVIEW_REQUIRED`
- `MOVE_ELIGIBLE`
- `MOVING`
- `MOVED_VERIFIED`
- `SKIPPED`
- `FAILED`

임의의 상태 전환을 허용하지 않는다.

이미 해당 채널에 설정한 이동 대상/확인된 처리 완료 글머리에 있는 글은 `SKIPPED / ALREADY_HANDLED`,
분석 후 다른 관리자가 이동한 글은 `SKIPPED / CATEGORY_CHANGED_EXTERNALLY`로 구별한다.
우리가 이동하지 않은 글을 `MOVED_VERIFIED`나 자체 이동 알림/건수로 기록하지 않는다.
이름/키워드만 확인되고 신고자 고유성이 미확인인 경우 `REPORT_VERIFIED`로 진행하지 않는다.

## 9.2 자동 이동 전 검사

이동 직전에 다음 사항을 재확인한다.

- 관리자 권한
- 게시글 존재 여부
- 현재 글머리
- 대상 글머리
- 동일 게시글의 기존 처리 상태
- 광고 판정 근거
- 프로그램 긴급 중지 여부

게시글 상태가 분석 당시와 달라졌다면 자동 이동을 중단하고 다시 검토한다.

현재 글머리가 이미 해당 채널에 설정한 이동 대상/검증된 처리 완료 글머리이면 즉시 건너뛴다.
다른 관리자의 이동이 확인되면 덮어쓰거나 원래 글머리로 복원하지 않는다.
단순 본문 변경/권한 상실과 확인된 외부 이동은 서로 다른 사유로 남긴다.

## 9.3 중복 처리 방지

게시글 식별자와 채널 식별자를 이용하여 중복 처리를 방지한다.

같은 게시글에 여러 신고가 들어와도 동시에 여러 번 이동하지 않는다.

서로 다른 브라우저 탭에서 ArcaGuard가 실행되는 상황도 고려한다.

로컬 작업 잠금과 처리 식별자를 사용하되, 브라우저 저장소만으로 완벽한 분산 잠금이 보장된다고 가정하지 않는다.

실제 조치 직전에 사이트의 최신 게시글 상태를 다시 확인한다.

관리자는 여러 명일 수 있고 서로 다른 PC/계정에서 동시에 작업할 수 있다.
로컬 기록이 없어도 사이트의 최신 글머리와 확인된 처리 이력이 기처리 판단의 근거다.
확인할 수 없는 과거 이동 이력이나 임의의 다른 글머리를 처리 완료로 추정하지 않는다.
신고 중복 키는 채널/대상 유형/대상 ID/안정적 신고자 식별값이며 관리자별로 다시 세지 않는다.
로컬 잠금만으로 서로 다른 PC의 정확히 한 번 실행을 보장하지 않는다.
검증된 사이트의 조건부 변경 기능이 없으면 채널별 자동 실행 담당 인스턴스 1개와
나머지 관찰/수동 검토 모드를 운영 대안으로 제공하고 동시 수동 조치의 잔여 경합을 명시한다.
응답이 불명확하면 현재 상태부터 읽고, 중복 요청 위험이 있는 조치를 자동 재시도하지 않는다.

## 9.4 조치 실패

자동 이동 요청이 실패하면 다음을 수행한다.

1. 성공으로 기록하지 않는다.
2. 현재 게시글 상태를 재확인한다.
3. 오류 원인을 기록한다.
4. 관리자에게 필요한 경우 알린다.
5. 중복 조치 위험이 있으면 재시도하지 않는다.

## 9.5 긴급 중지

관리자가 모든 자동 이동을 즉시 중지할 수 있어야 한다.

긴급 중지 이후에는 이미 시작한 작업도 가능한 범위에서 중단하고, 아직 실행되지 않은 관리자 조치는 수행하지 않는다.

# 10. 실제 사이트 검증

다음 사항은 현재 미검증 상태다.

- 신고 목록에 신고 원문이 표시되는지
- 신고 개수가 어떻게 제공되는지
- 신고 원문을 스크립트가 읽을 수 있는지
- 관리자 권한을 어떤 방식으로 확인할 수 있는지
- 글머리 변경 기능이 어떤 UI를 사용하는지
- 관리자 전용 휴지통이 일반 글머리와 같은 방식으로 처리되는지
- 관리 화면이 페이지 갱신 없이 동적으로 변경되는지

Codex는 검증되지 않은 기능을 임의로 완성 처리해서는 안 된다.

`docs/SITE_VERIFICATION.md`에 기능별로 다음 내용을 기록한다.

- 기능명
- 검증 상태
- 근거
- 확인한 화면
- CSS 선택자
- 데이터 접근 방법
- 접근 권한
- 오류 사례
- 최종 검증 날짜

관리 화면 접근이 불가능한 개발 환경에서는 Mock 데이터를 사용한다.

실제 관리자 화면이 확인되기 전까지 쓰기 기능은 비활성화한다.

- 특정 광고 업체를 비판하는 글
- 투자 상품을 정상적으로 비교하는 글
- 뉴스 기사에 광고 문구가 포함된 글
- 금융 용어가 많이 등장하는 분석 글
- 우연히 유사한 문자열이 포함된 게시글

정규식 또는 AI 결과 하나만으로 무조건 자동 이동하는 로직을 만들지 않는다.

## 11.4 실사이트 테스트

실제 관리자 계정과 테스트용 게시글이 준비되었을 경우에만 실행한다.

최초 실사이트 테스트는 읽기 전용으로 제한한다.

글머리 변경 테스트는 별도의 명시적인 승인 후 단일 테스트 게시글을 대상으로 실행한다.

실사이트 자동 테스트에서 임의의 일반 이용자 게시글을 이동하지 않는다.

테스트 채널은 `https://arca.live/b/prlvate`, 대상 글머리 이름은 `TEST`로 지정되었다.
실제 권한/글머리 확인과 개별 테스트 글 이동 승인은 여전히 별도로 필요하다.

- 유사도 민감도 설정
- 성능 최적화
- 테스트 코드 작성

완료 기준:

- `대@414출@$15권@$5유` 탐지
- `떄출꿘유` 유사도 후보 탐지
- 정상 문장 오탐 검증
- 검사 실행 시간 제한

## Phase 4 — 신고 감시 시스템

목표: 신고 호출어를 통한 자동 분석 시작

작업:

- 신고 목록 읽기

- 신고 링크/신고자 이름·계정 식별값/신고 내용 검증 및 `광고` 포함 검사
- 신고 임계값 설정
- 신고 대상 게시글 읽기
- 중복 처리 방지
- 스케줄러
- 오류 및 재시도 처리

완료 기준:

- 조건을 충족하는 신고만 분석
- 조건 미달 신고 제외
- 댓글 신고와 게시글 신고 구별
- 신고 자료 미확인 시 자동 이동 불가
- 실제 신고 접근이 불가능하면 Mock 테스트로 제한
- 사이트 현재 총수/사유를 사용하고 재조회 값을 누적 가산하지 않음 (별도 신고자 중복 집계 없음)

## Phase 5 — 관리자 설정 인터페이스

목표: 코드 수정 없이 설정 가능한 UI

추가 범위: 주제/규칙/예외 CRUD, 주제별 호출 조건·검토/이동 방식·대상 상속/선택,

작업:

- 대시보드

- 신고 설정
- 정규식 편집기

- 위험도 설정
- 처리 모드
- 알림 설정
- 처리 기록
- JSON 설정 백업 및 복원

완료 기준:

- 모든 주요 설정 변경 가능
- 설정 영구 저장
- 채널별 설정 분리
- 규칙 테스트 가능

## Phase 6 — 이미지 분석

완료 기준:

- 정상 차트 이미지 오탐 테스트
- OCR 실패 처리
- 유료 API 없음

## Phase 7 — 관리자 글머리 변경

목표: 검증된 관리자 기능으로 탭 이동

- 상태 검증 성공

모든 조건이 검증되기 전까지 자동 이동 모드는 비활성화 상태를 유지한다.

# 16. 최초 실행 명령

이 명세서를 읽은 Codex는 다음 작업만 수행한다.

**Phase 0 — 프로젝트 기반 구축**

1. 현재 디렉터리와 Git 상태를 확인한다.
2. 기존 파일이 있다면 보존한다.
3. 필요한 프로젝트 구조를 생성한다.
4. 루트 `AGENTS.md`를 작성한다.
5. 아카라이브 어댑터 전용 `AGENTS.md`를 작성한다.
6. `docs/PLAN.md`에 Phase 0~9 개발 계획을 작성한다.
7. Vite 및 vite-plugin-monkey를 구성한다.
8. Tampermonkey 메타데이터를 작성한다.
9. 기본 실행 진입점을 만든다.
10. 간단한 ArcaGuard 테스트 UI를 구현한다.
11. ESLint와 Vitest를 구성한다.
12. 빌드 및 테스트를 실행한다.
13. 생성한 파일과 결과를 보고한다.
14. 사용자 승인 전 다음 Phase로 넘어가지 않는다.

Phase 0에서는 실제 게시글의 글머리를 변경하거나 관리자 기능에 쓰기 요청을 보내지 않는다.

**최종 목표는 광고 신고 자동 분석, 우회 광고 탐지, 무료 이미지·AI 분석 및 안전한 글머리 이동을 지원하는 범용 아카라이브 관리자 보조 도구를 완성하는 것이다.**

단, 최종 게시글 삭제와 이용자 차단은 반드시 관리자가 직접 수행한다.
