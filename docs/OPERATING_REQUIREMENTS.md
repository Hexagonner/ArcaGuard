## OP-01. 사용자가 선택하는 채널과 대상

- 사용자는 설정 화면에서 사용할 채널을 직접 추가/변경/삭제하고, 각 채널의 이동 대상 탭을
  독립적으로 선택/변경할 수 있어야 한다. 특정 채널/탭 전용 프로그램으로 제한하지 않는다.
- 최초 실행의 등록 채널과 이동 대상은 미설정이다. 예시/테스트 설정을 자동 등록하지 않는다.
- 선택할 수 있는 범위는 실제 존재하고 현재 관리자에게 필요한 권한이 있는 채널/글머리다.
  채널에서 조회한 실제 글머리 목록을 표시해 선택하며 내부 ID나 코드를 사용자가 직접 수정할 필요가 없어야 한다.
- 채널마다 대상 이름과 검증된 글머리 ID를 보관하고 같은 이름의 다른 채널 글머리와 혼동하지 않는다.
- 설정 변경 시 해당 채널의 대기 작업은 이전 설정으로 이동하면 안 된다. 작업의 채널/대상/
  설정 버전을 이동 직전에 재확인하고 변경된 작업은 취소 또는 재검토한다. 새 대상을 임의로 적용해 재이동하지 않는다.
- 대상이 사라졌거나 권한/목록을 확인하지 못하면 이동을 중단하고 다시 선택하도록 안내한다.
  채널/대상이 미설정이면 자동 이동할 수 없다. 다른 채널의 설정에는 영향을 주지 않는다.
- 사용자 의도는 분석 후 관리자 전용 격리 탭으로 이동하고 관리자가 사후 조치하는 것이다.
  관리자만 볼 수 있는 분류와 실제 삭제 상태를 구별한다. 대상은 본문 보존/관리자 접근/
  일반 사용자 접근 제한/분류 변경 의미를 검증해야 하며 실제 삭제 효과가 있으면 자동 대상으로 사용하지 않는다.

### 개발 테스트용 선택 예시 (고정값/기본값 아님)

- 테스트 채널: **https://arca.live/b/prlvate**. 채널 표기는 `prlvate`이며 `private`가 아니다.
- 해당 채널에서 광고 판정 기준을 충족한 미처리 글의 이동 대상 이름: **TEST**.
- 사용자가 해당 채널의 관리자임을 밝혔다. 상태는 `user-provided`이며 사이트 권한 검증은 `unverified`다.
- TEST의 실제 글머리 ID/존재/선택 가능 여부/이동 의미는 미검증이다. 조회한 목록에서
  정확한 채널/대상을 확인해야 한다. 이름이 없거나 복수 후보이면 임의 선택하지 않는다.
- 사용자는 TEST를 휴지통처럼 관리자만 볼 수 있도록 구성했고 생성·설정 완료를 확인했다.
  출처는 사용자 확인이며 실제 접근 제한/ID/삭제 없는 보존 동작은 직접 검증 전이다. 자동 이동 적격 판정은 보류한다.
  신고 화면에서 직접 변경하는 기능은 없고 대상 게시글에서 수동 변경한다는 사용자 설명이 있다.
  사용자가 확인한 순서는 수정 → 글머리 선택 → 저장이다. 실제 DOM/전송 범위/백그라운드 요청은 검증 전이다.
  글머리 변경으로 제목/본문이나 다른 관리자의 동시 편집을 덮어쓰지 않는지 확인해야 한다.
- 이 값은 테스트용 채널 설정으로 사용할 요구사항이며 현재 실행 설정을 생성한 것은 아니다.
  다른 채널의 설정/기본 대상/관리 권한에 영향을 주지 않는다.
- 지정 채널이라는 이유로 채널 전체의 글을 시험 이동하지 않는다. 최초 쓰기 테스트에는
  단계 승인, 실제 UI/권한 확인, 사용자가 지정한 단일 테스트 글과 쓰기 승인이 필요하다.

## OP-02. 신고 입력 검증

개별 신고에서 다음 정보를 사이트가 제공한 필드로 읽고 검증 결과를 분리한다.

Phase 1에서 사용자가 제공한 목록에는 대상/작성자/신고자/상태/상세 링크가 있고,
상세 화면에 사유가 표시된다고 확인했다. 현재는 사용자 제공 근거이며 DOM은 미검증이다.
향후 목록과 상세를 읽어 결합하되 **글 작성자와 신고자를 혼동하지 않는다**.
상세 사유를 읽지 못하면 목록의 이름/제목/상태로 사유나 `광고` 일치를 채우지 않는다.

- `targetUrl`: 신고된 글/댓글의 실제 링크. 신고 내용에 임의로 적힌 링크를 대상이라고 믿지 않는다.
- `channelId`, `targetType`, `articleId`, 필요한 경우 `commentId`: 검증된 대상 식별 정보.
- `reporterDisplayName`: 사이트가 표시한 신고자 이름. 공백/누락 여부를 검사하고 화면에서 확인 가능해야 한다.
- `reporterProfileUrl`/계정 표시 정보: 사이트가 제공하는 경우 출처를 구별해 보관한다.
  로컬 중복 집계용 고유 키를 필수로 만들지 않는다.
- `reasonText`: 실제 신고 내용. 누락/읽기 실패와 정상적으로 읽은 내용을 구별한다.
- `keywordMatched`: 신고 내용에 기본 키워드 **광고**가 포함되는지 여부.
- 비광고 주제에는 사용자가 설정한 주제별 신고 호출 조건을 평가한다. 광고는 기본값이며 고정된 유일 주제가 아니다.
- 사이트가 제공하는 경우 `reportId`, 신고 시각, 철회/유효 상태, 조회 범위/완전성.
- 필수 정보별 `verified`, `missing`, `unsupported`, `error` 등 검증 상태와 근거.

대상 링크 검증은 사이트 어댑터에서 확인한 URL 구조에 한해 구현한다. HTTPS arca.live와
등록한 채널/실제 대상 ID를 확인하고 외부 호스트/다른 채널/실행 가능한 URL은 제외한다.
추적 파라미터가 달라도 같은 실제 대상이면 같은 키로 처리하되 댓글 식별자는 보존한다.
단순히 모든 쿼리/fragment를 지우거나 URL 형태를 추측해 댓글을 부모 글로 바꾸지 않는다.
서버 리다이렉트 등으로 대상이 달라지면 최종 대상도 확인한다.

이름과 계정 표시 정보는 신고자가 사유에 적은 문자열이 아니라 사이트 필드에서 얻는다.
임의의 계정 ID를 만들지 않으며 안정적 고유 키의 부재만으로 사이트 신고 수를 사용할 수 없다고 판단하지 않는다.
대상 링크/신고자 이름/신고 내용이 누락되면 검토 대상으로 표시하고 필수 입력을 임의로 채우지 않는다.

## OP-03. 사이트 제공 신고 수와 키워드

2026-10-24 사용자가 동일 계정의 동일 대상 신고가 1회로 제한되고 받은 신고 수도 확인 가능하다고 밝혔다.
이 확인에 따라 **사이트의 현재 총 신고 수를 사용하고 별도 신고자 중복 집계 기능은 만들지 않는다**.
에이전트의 사이트 직접 검증과 사용자 확인은 구별하며, 과거의 로컬 고유 신고자 집계 계획은 이 절로 대체한다.

- `siteReportCount`: 해당 대상에 대해 사이트가 현재 표시하는 총 신고 수. 기본 임계값은 1건이다.
- `keywordReportCount`: 현재 읽은 신고 사유 중 주제 호출어가 포함된 항목 수. 기본 임계값은 1건이다.
  신고자별 로컬 기여 키/누적 장부를 만들지 않는다. 여러 주제의 수를 합산하지 않는다.
- 현재 값/출처/조회 시점/검증 상태를 저장하는 스냅샷 방식이다. 같은 페이지를 다시 읽을 때
  `이전 값 + 읽은 값`으로 더하지 않고 최신 값으로 대체한다. 여러 관리자/탭의 조회 값도 합산하지 않는다.
- 총 신고 수의 파싱/대상 대응과 사유 행의 읽기 범위는 확인한다. 자료 누락/접근 실패/값 미확인 시
  0건으로 채우거나 누락된 사유를 키워드 일치로 가정하지 않는다. 이전 확인 값과 현재 미확인 상태를 구별한다.
- 이름 변경/표시 형식 차이/안정적 계정 키의 부재 때문에 사이트 수를 다시 계산하거나 차단하지 않는다.
- 같은 알림/대상 작업의 중복 실행 방지와 기처리 글 재이동 방지는 계속 필요하다.
  이는 불필요해진 ‘동일 신고자의 반복 신고 수 보정’과 다른 책임이다.
- 신고 목록의 보이는 행 수는 해당 게시글의 신고 수가 아니다. 전체/대기/완료/이전 내역의 실제
  읽기 범위를 확인하고 대상 상세의 사이트 총수로 판단한다. 과거 내역 재조회도 누적하지 않는다.
  작성자와 신고자 표시가 같아도 그 자체로 신고를 무효화하거나 광고 근거로 가산하지 않는다.

기본 일치는 신고 내용을 문자열로 확인한 뒤 `광고` 포함 여부를 검사한다.
`광고)`, `광고 의심`, `사진에 광고가 있습니다`는 일치한다.
제목/링크/신고자 이름에만 `광고`가 있으면 불일치다.
`광고가 아닌 것 같습니다`도 문자열 일치에는 포함되지만 게시글 광고 근거에는 포함하지 않는다.
OP-10의 신고 기준 모드에서는 문맥 판정 없이 이 일치 수가 조치 조건에 사용됨을 설정/미리보기에 명시한다.
사용자 설정으로 키워드를 바꿀 수 있으며 복잡한 정규식은 기존 안전 요구사항을 따른다.
사이트의 신고 입력 제한을 ArcaGuard가 다시 구현하거나 수정하지 않는다.

## OP-04. 복수 관리자와 이미 처리된 글

관리자는 여러 명일 수 있다. 각 계정의 해당 채널 읽기/이동 권한은 개별 검증한다.
어느 관리자/PC가 처리했든 확인된 기처리 대상에 추가 이동/재시도/성공 알림을 발생시키지 않는다.

향후 처리 순서는 다음과 같다.

1. 신고 입력/사이트 제공 총수/사유 호출 조건이 유효한지 확인한다.
2. 대상의 최신 글머리/존재/상태를 읽는다. 이미 해당 채널에 설정한 이동 대상 또는 검증된 처리 완료 글머리이면 건너뛴다.
   신고 화면의 `처리 상태: 완료`는 이 글머리 검증과 별개이며 그것만으로 글 이동/격리 완료를 추정하지 않는다.
3. 미처리 대상의 선택된 OP-10 조치 정책과 예외를 평가한다. 신고 기준 모드는 광고 분류를 요구하지 않고,
   AI 확인 모드는 현재 글에 대한 유효한 로컬 AI 결과를 요구한다. 당시 글머리 ID와 상태 지문을 기록한다.
4. 이동 직전에 로그인/권한/최신 글머리/선택된 채널·대상/설정 버전/긴급 중지를 다시 확인한다.
5. 다른 관리자가 이동한 것으로 확인되면 덮어쓰지 않고 건너뛴다.
6. 상태가 그대로이고 선택된 조치 정책/예외/신고/권한/실행 모드/정책 충돌 조건을 모두 만족할 때만 승인된 조치를 한다.
7. 조치 후 현재 상태를 읽어 확인한다. 실패/시간 초과/불명확 응답이면 쓰기 재시도부터 하지 않는다.

- `SKIPPED / ALREADY_HANDLED`: 최초 조회/이동 직전 이미 설정된 이동 대상 또는 확인된 처리 완료 글머리.
- `SKIPPED / CATEGORY_CHANGED_EXTERNALLY`: 분석 후 다른 관리자에 의한 이동이 확인됨.
- 단순 내용 변경/삭제/권한 상실/조회 실패는 기처리 성공으로 취급하지 않고 검토/실패로 남긴다.
- `MOVED_VERIFIED`는 우리가 실행한 이동과 결과를 확인한 경우에만 사용한다.
  애매한 요청 후 설정된 대상 탭에 있어도 실제 실행 주체가 불명확하면 자체 성공으로 단정하지 않는다.
- 다른 관리자가 이미 이동한 사실을 확인했으면 원복하거나 현재 설정한 대상으로 강제 이동하지 않는다.
  최초 조회 이전의 이력은 검증된 이력이 있을 때만 사용한다. 임의의 다른 탭은 처리 완료 표시가 아니다.
- 사용자가 나중에 글을 원래 탭으로 되돌려도 과거 처리 건을 자동 재이동하지 않는다.
  기록과 현재 상태가 충돌하면 관리자 검토로 보내고 명시적인 재검토 없이는 다시 조치하지 않는다.
- 이동 대상 설정을 바꿔도 과거 기처리 이력이 사라지지 않는다. 예전 대상에 있던 처리 글을
  새 대상에 없다는 이유만으로 미처리로 바꾸거나 자동 재이동하지 않는다.

여러 PC의 로컬 저장소/GM 값은 공유 잠금이 아니다. 재조회와 쓰기 사이에 다른 관리자가
조치할 수 있으므로 이 설계만으로 중복 요청을 절대 0회로 만들거나 정확히 한 번 실행을 보장하지 않는다.
사이트가 검증된 원자적/조건부 변경 기능을 제공하면 그 범위에서 활용할 수 있으나 API를 추측하지 않는다.
없는 경우 **채널별 자동 실행 인스턴스 1개 + 나머지 관찰/수동 검토**를 운영 대안으로 설계한다.
이 역시 원격 관리자/수동 조치에 대한 완전한 잠금이 아니며 안전성 검증 전 자동 이동은 계속 OFF다.

## OP-05. 정보 보관과 채널 격리

- 신고자 이름/내용은 검증과 관리자 검토에 필요한 범위에서만 접근한다.
- 신고자별 집계 키/장부를 만들지 않으며 프로필 표시 정보도 사용자 추적 용도로 사용하지 않는다.
- 인증 토큰/쿠키/비밀번호를 계정 키로 사용하거나 저장하지 않는다.
- 기본 로그/내보내기에는 신고 원문/이름/계정 식별값을 자동 복사하지 않는다. 필요 시 합계와
  판정 사유를 사용한다. 개인정보 제거를 위한 해시를 익명화 보장으로 설명하지 않는다.
- 집계/중복 방지 상태와 최근 1,000건 처리 로그의 수명은 구별한다. 로그 정리만으로
  기처리 글이 새 대상으로 되거나 중복 신고가 다시 더해지면 안 된다.
- 보관 기한 만료/상태 손상 시 새로 검증된 현재 신고 집합과 사이트 상태를 읽어야 하며,
  재구성할 수 없으면 자동 처리를 중단한다. 오래된 개인정보를 무기한 보관하는 방식은 쓰지 않는다.
- 테스트에는 가짜 계정 A/B와 합성 신고 내용을 사용한다. 실제 비공개 신고/신고자 이름을
  Fixture/스크린샷/문서/외부 서비스로 복사하지 않는다.

## OP-06. 구현 단계와 검증 책임

- Phase 1: 지정 채널의 허용된 읽기 조사에서 URL/신고 필드/계정 식별 가능 여부/
  글머리 목록/상태/이력 제공 여부를 확인한다. 사용자 제공 정보와 실측 근거를 분리한다.
- Phase 4: 신고 필드/사이트 총수 검증, 최신 스냅샷 교체, 작업 중복 실행 방지, 댓글 구분 및 누락 시 중단을 구현한다.
- Phase 5: 사용자의 채널 추가/변경/삭제와 채널별 대상 탭 선택/변경,
  사이트 총수와 키워드 포함 사유 수/검증 상태/기처리 사유와 관찰 모드를 표시한다.
- Phase 7: 승인된 단일 글에서 최신 상태 재조회, 외부 이동 건너뛰기, 결과 검증과 경합 한계를 검사한다.
- Phase 9: 복수 계정/탭/PC, 로그 정리/재시작/설정 복원 후 중복 처리 회귀를 검증한다.

인수 시나리오는 [TEST_PLAN.md](TEST_PLAN.md)의 `RPT-*`, `MOD-*`, `CFG-*`를 따른다.
현재 위 계약에 대한 동작 테스트/실사이트 확인은 수행하지 않았다. 구현한 것처럼 보고하지 않는다.

## OP-07. 백그라운드 처리와 사용 방해 금지

광고 글의 이동은 서버의 글머리/분류를 바꾸는 조치이며 브라우저 탭을 이동하는 기능이 아니다.
관리자가 글을 읽거나 작성하거나 다른 브라우저 탭을 사용하는 동안에도,
실행 가능한 Userscript 인스턴스가 검증된 백그라운드 요청으로 처리해야 한다.
감시와 자동 이동은 여전히 기본 OFF이며 기존 신고/주제/권한/기처리/상태 검증 조건을 모두 적용한다.

- 자동 처리로 현재 URL/브라우저 선택 탭/방문 기록을 변경하거나 페이지를 새로고침하지 않는다.
  새 탭/창/팝업/보이는 관리 화면을 열거나 자동으로 닫지 않는다. 숨겨진 탭을 여는 방식도 사용하지 않는다.
- 스크롤, 포커스, 커서/선택 범위, 입력 중인 글/댓글/검색어/IME 조합을 건드리지 않는다.
  현재 읽는 글을 강제로 제거하거나 목록을 재배치하지 않는다. 결과는 기록에 반영하고
  사이트 자체의 정상 갱신 외에 현재 화면 갱신을 강제하지 않는다.
- 자동 조치나 결과 검증을 위해 실제 화면의 관리 메뉴/드롭다운/이동 버튼을 대신 누르지 않는다.
  관리자 UI에서 관찰·검증한 허용된 요청 방식과 필요한 권한을 확인한 뒤 별도 어댑터로 실행한다.
  미확인 API 추측이나 인증 자료 저장으로 이를 대체하지 않는다.
- 백그라운드 요청 및 결과 재조회가 불가능하거나 재로그인/사용자 확인이 필요하면
  해당 자동 처리를 중단하고 검토 대기로 남긴다. 화면 조작으로 전환하거나 로그인 창을 강제하지 않는다.
  관리자에게 직접 이동을 제안할 수는 있지만 수동 작업과 자동 처리 성공을 구별한다.
- 기본 성공 안내는 처리 기록과 배치가 바뀌지 않는 조용한 상태 표시다. 작업마다 패널을 열거나
  포커스를 가져오거나 모달/토스트/OS 알림/소리를 발생시키지 않는다. 선택적 개별 알림도
  명시적 사용자 설정과 중복 억제/빈도 제한을 적용하며 화면이나 포커스를 바꾸지 않는다.
- 감시/조회/분석은 제한된 작업 큐와 요청 빈도/동시성 제한을 사용한다. 같은 채널의 쓰기는 직렬화하고
  오류/제한 응답에는 백오프한다. DOM 전체를 반복 스캔하거나 무제한 요청/재시도를 하지 않는다.
  OCR/AI/무거운 문자열 처리는 가능한 Worker 및 분할 실행과 작업량/시간 제한으로 입력 응답을 보호한다.
  부하가 커지면 자동 처리량을 줄이거나 일시 중지한다. 메인 스레드의 긴 동기 처리를 허용하지 않는다.
- 사용자는 평소처럼 사이트를 이용할 수 있어야 하며, 긴급 중지/감시 OFF는 처리 대기열에도 적용한다.
  이미 전송한 서버 요청을 취소로 원복했다고 가정하지 않고 결과 재조회와 상태 기록을 수행한다.

여기서 백그라운드는 **사용자 화면을 점유하지 않는 페이지 내 비동기 실행**이다.
일반 Userscript는 브라우저 종료/실행 페이지 종료/탭 폐기/PC 절전 동안 상시 실행을 보장하지 않는다.
다른 탭 사용 중에도 브라우저의 타이머 제한/탭 정지로 처리가 지연될 수 있으므로 정확한 주기나 즉시 처리를 약속하지 않는다.
재개 시 최신 신고/설정/권한/글 상태를 다시 확인하고, 밀린 작업을 한꺼번에 발송하지 않는다.
이 한계는 별도 서버나 다른 확장 구조를 도입한 것으로 숨기지 않고 설정/운영 안내에 설명한다.

Phase 1에서 백그라운드 조치/결과 읽기의 가능성을 조사하고, Phase 4/6/8에서 감시·분석 부하를 제한한다.
Phase 5에서 조용한 안내/선택적 알림을, Phase 7/9에서 무방해 조치/중단/재개와 사용 중 응답성을 검증한다.
인수 기준은 `TEST_PLAN.md`의 `BKG-*`다. 현재 백그라운드 이동 기능은 구현/실사이트 검증 전이다.

## OP-08. 버튼 표시·고정 및 전용 관리자 화면

이 절은 사용자가 추가로 승인한 UI 보완이며, 구현 범위는 화면 설정에 한정한다.

- 최초 상태는 버튼 표시 ON/위치 고정 OFF다. 기존 좌표를 유지하며 표시/고정 값을 별도 버전으로 검증·저장한다.
- 위치 고정 ON이면 드래그/Alt + 방향키/기본 위치 초기화를 막되 버튼 클릭과 설정 열기는 허용한다.
  화면 크기 변경 시 보이는 영역으로 배치하는 기존 동작은 유지한다.
- 표시 OFF이면 버튼과 간이 패널을 숨긴다. 새로고침 후에도 유지하며 숨김은 감시/자동 이동 설정을 변경하지 않는다.
  현재 감시/자동 이동 기능 자체는 미구현이고 OFF다.
- 관리자는 간이 패널의 ‘관리자 설정 열기’, Alt + Shift + G 또는 설치된 스크립트의
  Tampermonkey 메뉴로 전체 화면 설정을 연다. 숨겨진 상태에서도 단축키/메뉴는 복구 경로로 남긴다.
- 관리자 화면은 사이트 내 Shadow DOM UI이며 별도 서버/아카라이브 관리자 URL을 만들지 않는다.
  사이트 권한을 증명하거나 제공하지 않고 화면 설정과 현재 미검증 상태만 표시한다.
- 사용자 요청에만 열고 새 탭/페이지 이동/네트워크 요청을 하지 않는다. 닫기/Escape는 가능한 이전 포커스로 돌아간다.
  열린 동안 Tab을 설정 화면 안에 유지하고 IME 조합 중에는 전역 단축키로 끼어들지 않는다.
- 저장 차단 시 현재 화면에 적용하고 영구 저장 불가를 안내한다. 손상된 표시/고정 자료는 안전한 기본값으로 복구한다.
  같은 origin/브라우저 범위의 UI 선호이며 계정·채널 운영 설정이나 다른 탭 즉시 동기화 기능은 아니다.

## OP-09. 사이트 신고 알림을 이용한 백그라운드 검토

사용자가 사이트 고유 신고 알림과 상세 원문 필드를 제공했다. 이는 수집 경로의 사용자 제공 근거이며,
현재 감시/탭 이동 구현이나 실제 DOM·권한 검증 완료를 뜻하지 않는다.
사용자는 이번 설명의 ‘삭제’가 **기존처럼 지정 탭(TEST 등)으로 이동**한다는 뜻임을 확인했다.
자동 게시글/댓글 삭제와 계정 차단 금지는 유지한다.

- 사이트 신고 알림은 새 분석 후보를 찾는 신호다. 알림 메시지/읽지 않은 알림 수를
  신고 수나 광고 근거로 사용하지 않는다. 총 신고 수는 OP-03의 사이트 값을 사용한다.
  사이트가 보내는 새 신고 알림과 ArcaGuard가 보내는 처리 알림도 구별한다.
- 사이트의 신고 알림 수신 여부는 관리자 선택이다. ArcaGuard가 사이트 알림 설정을 대신 켜거나
  알림 패널을 강제로 열지 않는다. 감시/자동 이동도 명시적 활성화 전에는 OFF다.
- 검증된 알림 자료에서 같은 origin/선택한 채널의 신고 상세 링크를 확인하고,
  `(channelId, reportId)`로 중복 이벤트를 합쳐 제한된 읽기 대기열에 넣는다.
  reportId는 불투명 식별자이고 대상 글 ID/신고자 ID와 구별한다.
- 알림을 자동 클릭하거나 현재 창을 신고 상세로 이동시키지 않는다. 검증된 비동기 읽기 방식으로
  상세의 유형/대상/작성자와 신고자별 사유를 확인한다. 알림이 불완전하거나 꺼져 있으면
  권한이 검증된 신고 목록을 제한된 주기로 대조할 수 있어야 하며 알림만으로 목록 완전성을 보장하지 않는다.
- 상세의 `ARTICLE` 예시를 모든 유형으로 일반화하지 않는다. 댓글/미지원 유형을 부모 게시글로 대체하지 않는다.
  총 신고된 횟수는 사이트 현재 값으로 사용하고 사유는 OP-03의 현재 스냅샷으로 확인한다.
  신고자별 반복 신고를 다시 제거하는 장부는 만들지 않는다.
- 신고 사유의 `광고`는 신고 기준 정책의 호출 조건이다. 대상 글의 실제 근거/예외/권한/설정/모드와 현재 글머리를
  구별한다. 조치 자격은 OP-10의 선택된 정책으로 평가하며 신고 기준 모드에서는 내용 분류가 필수가 아니다.
  예외/권한/설정/현재 글머리를 확인하고 기처리/외부 이동/삭제 대상을 제외한 뒤 후속 승인된 구현에서만 옮긴다.
  이동 전 최신 상태와 이동 후 결과 재조회는 생략하지 않는다.
- 알림의 읽음 처리/모두 읽기는 자동 수행하지 않는다. 신고의 처리 완료 제출도 글머리 이동과 별개이며,
  후속 OP-11의 독립 설정/검증 조건으로만 허용한다. 상세 읽기가 사이트 읽음 상태 등을 바꾸는지도 검증 전이며,
  무방해 읽기 조건을 확인하지 못하면 해당 경로를 사용하지 않고 검토 대기로 남긴다.
- 중복/과거 알림, 다중 탭/복수 관리자, 늦게 도착한 알림도 작업 중복 방지와 기처리 조건을 적용한다.
  알림 재전달/새로고침/재연결 때문에 재이동하거나 성공 카운터를 중복 증가시키지 않는다.
- 브라우저 비활성/정지/절전 중 즉시 수신·정시 처리를 보장하지 않는다. 재개 시 최신 신고와 상태를
  제한된 큐로 확인한다. 사용자 화면/입력/스크롤을 보존하는 OP-07은 계속 적용한다.

Phase 1은 알림/상세/읽음 부작용/권한을 조사하고, Phase 4는 후보 감시·재대조·중복 억제를,
Phase 7은 별도 승인 후 실제 백그라운드 글머리 변경을 검증한다. 이 절로 후속 Phase를 승인하지 않는다.

### 사용자 화면을 점유하지 않는 읽기의 구현 계획

- 알림 수신은 사이트가 이미 제공하는 검증된 읽기 전용 자료를 관측한다. DOM 자료가 있다면
  해당 알림 영역만 관측하며 사이트의 fetch/WebSocket 구현을 교체하거나 알림 패널을 자동으로 열지 않는다.
  실제 전달 방식은 아직 미검증이다. 자료가 없으면 허용된 신고 목록의 설정 주기 대조를 사용한다.
- 같은 사이트의 신고 상세 주소에 비동기 읽기 요청을 보내 응답만 받는 방법을 검증한다.
  브라우저가 기존 동일 origin 세션을 처리하며 스크립트가 비밀번호/쿠키/인증 토큰을 직접 읽거나 저장하지 않는다.
  이는 [Fetch의 일반 동작](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)이며
  해당 신고 주소의 접근/읽음 부작용/CSP/권한까지 지원됨으로 확인한 것은 아니다.
- 응답에서 필요한 텍스트/링크만 읽고 현재 페이지에 삽입하거나 응답 속 스크립트를 실행하지 않는다.
  현재 URL/선택 탭/스크롤/포커스/입력/초안을 보존하고 알림 읽음 상태를 대신 바꾸지 않는다.
- HTML 해석은 추가 이미지/프레임/종속 리소스나 외부 링크 목적지를 자동 요청하지 않는 방식으로 검증한다.
  [MDN DOMParser 문서](https://developer.mozilla.org/en-US/docs/Web/API/DOMParser/parseFromString)는
  분리된 문서에서도 리소스 다운로드 가능성을 명시하므로 비삽입만으로 무요청을 보장하지 않는다.
  파싱/CSP/Trusted Types 실패는 보류하며 활성 DOM 삽입/숨겨진 프레임으로 우회하지 않는다.
  이후 승인된 OCR 이미지 읽기는 별도 수량/크기/출처 제한으로 검증한다.
- 요청은 제한된 큐/시간 제한/오류 백오프를 적용하고 큰 문서 분석은 분할/Worker로 입력 응답을 보호한다.
  비동기 네트워크 요청만 쓴다고 무거운 분석까지 자동으로 무방해가 되는 것은 아니다.
- 검증된 읽기와 조치 방식이 없으면 현재 창을 대신 조작하지 않고 대기/검토로 남긴다.

## OP-10. 신고 기준 / AI 확인 조치 정책 선택 (설계 / 미구현)

2026-10-24 사용자가 두 가지 이동 모드를 선택할 수 있도록 요청했다.
이 절은 기존의 ‘모든 이동에 본문 광고 점수/독립 근거 필수’ 조건을 선택된 정책에 한해 대체한다.
신고를 게시글 자체의 광고 증거로 바꾸는 것이 아니라 관리자가 선택한 격리 조건으로 사용한다.

### 설정과 화면

- 채널별 광고 주제에 `actionPolicy`를 두고 **신고 기준 이동 / AI 확인 후 이동** 중 하나만 선택한다.
  두 독립 ON/OFF 스위치로 두 정책이 동시에 활성화되거나 AI 조건이 우회되지 않게 한다.
  주제별 재설정이 있으면 채널 기본값 상속 여부와 최종 적용값을 표시한다.
- `executionMode`의 Simulation/관리자 검토/자동 이동은 별도 설정이다.
  정책 선택만으로 자동 이동이나 감시를 켜지 않는다. 최초/손상 설정 복구/가져오기는
  감시 OFF, Simulation, 자동 이동 OFF이며 기본 정책 후보는 AI 확인 후 이동이다.
- `minSiteReports = N`은 현재 사이트 총 신고 수 기준이며 사용자가 정하는 양의 안전한 정수다.
  신고 기준 모드의 `minKeywordReports = K`는 현재 사유 중 호출어 포함 수이며 기본값 1, N 기본값도 1이다.
  각 값은 유한한 양의 안전한 정수로 검증하며 공백/0/음수/소수/잘못된 정책 값은 자동 실행을 차단한다.
- 기본 호출어는 `광고`이며 사용자 변경을 지원한다. N건은 ‘전체 신고 수’이고 K건은 ‘호출어 포함 사유 수’로
  이름을 분리한다. 신고자 중복 장부나 관리자별 합산은 만들지 않는다.
- AI 설정 OFF/모델 미준비이면 AI 정책을 저장해 두는 것은 가능하지만 실행 불가 사유를 표시한다.
  실행 가능한 것으로 보이게 하거나 신고 기준 정책으로 자동 전환하지 않는다.

### 정책 A — 신고 기준 이동 (`REPORT_THRESHOLD`)

- 조건: 검증된 현재 `siteReportCount >= N` **그리고** `keywordReportCount >= K`.
  예: N=3, K=1이면 총 신고 3건 이상이며 하나 이상 사유에 `광고`가 있어야 한다.
- 조건을 충족하면 AI/본문 광고 점수/최소 광고 근거 수를 기다리지 않고 격리 이동 후보가 된다.
  AI/OCR 미설치만으로 이 정책을 차단하지 않는다. 예외 검사에 필요한 자료가 없으면 여전히 보류한다.
- 결과는 `신고 조건 충족`으로 기록하며 AI 광고 확정이나 내용 분석 양성으로 표시하지 않는다.
  ‘바로’는 추가 광고 분류를 생략한다는 뜻이며 아래 공통 검증과 제한된 작업 큐를 생략하지 않는다.

### 정책 B — AI 확인 후 이동 (`AI_CONFIRMED`)

- 조건: 검증된 현재 `siteReportCount >= N` **그리고** 현재 게시글에 대한 유효한 로컬 AI 광고 판정.
  사용자 문장에 따라 이 정책에는 신고 사유의 `광고` 포함/K 임계값을 필수로 요구하지 않는다.
  필수 신고 대상/신고자 이름/사유 출처 검증은 그대로 유지한다.
- AI는 신고 사유나 신고 수를 본문 광고 근거로 받아 분류하지 않고 대상 글의 검증된 내용만 분석한다.
  규칙 결과는 보조 자료로 표시할 수 있지만 AI 양성 판정을 대신하거나 별도 고정 점수/근거 수로
  이 정책을 몰래 바꾸지 않는다. 적용 가능한 예외는 두 정책 모두 우선한다.
- 판정은 `광고 / 비광고 / 판단 불가 / 오류`를 구별한다. AI OFF/미지원/모델 미준비/시간 초과/
  필수 입력 누락/잘못된 출력/낮은 신뢰도는 검토 대기이며 광고로 간주하거나 A로 강등하지 않는다.
  비광고이면 이동하지 않는다. 모델별 한국어 성능/양성 기준을 후속 AI 단계에서 검증하기 전 자동 실행은 불가하다.
- AI 결과는 채널/글 식별자/내용 지문/모델·정책 버전에 묶는다. 내용이 바뀌거나 결과가 오래되면
  재확인하며 과거 글/다른 글/다른 채널의 결과로 조치하지 않는다. 외부 AI로 자료를 보내지 않는다.

### 공통 검증과 변경

- 두 정책 모두 유효한 게시글 신고, 현재 자료/대상, 채널별 권한, 검증된 격리 대상, 예외,
  기처리/외부 이동 제외, 설정 버전, 긴급 중지, 검증된 백그라운드 요청과 결과 재조회가 필수다.
  댓글 신고를 부모 게시글 이동으로 바꾸지 않는다. 자동 삭제/차단/알림 읽음 처리도 수행하지 않는다.
- 예외 검사에는 필요한 내용/작성자/링크 등의 검증된 자료만 사용한다. A에서 AI가 필요한 예외를
  실행할 수 없다면 예외를 생략하지 않고 보류한다. 주제 간 목적지 충돌은 관리자 검토로 보낸다.
- 이동 직전에 사이트 수/필요 사유, 권한/글 상태/정책을 재확인한다. N 아래로 줄거나 A의 K가
  미충족이면 이동하지 않는다. B는 현재 글과 AI 결과의 내용 지문도 일치해야 한다.
- 정책/N/K/호출어/예외/AI 모델·판정 기준 변경은 설정 버전을 바꾸고 미전송 대기 작업을 취소/재평가한다.
  기존 설정 가져오기에 actionPolicy가 없다고 A를 선택하지 않으며 자동 실행 OFF 상태로 명시적 재선택을 요구한다.
  이미 전송한 요청은 취소로 원복됐다고 가정하지 않고 결과 확인을 계속한다.
- 정책/조건 충족 사유와 적용 예외/최종 결과를 조용한 기록에 남긴다. A와 B의 성공 통계를 구별하고,
  한 글을 두 정책/복수 주제 때문에 여러 번 이동시키지 않는다.
- 구현 시점: Phase 4 신고 자료/분기, Phase 5 설정·상속·검증 UI, Phase 7 조치·재검증,
  Phase 8 로컬 AI 성능/결과 계약. AI 정책은 Phase 8 검증 완료 전 실행 불가다.
  현재 Phase 1은 설계만 기록하며 후속 구현/실사이트 쓰기를 시작하지 않는다.

## OP-11. 신고 처리 카테고리·버튼·답변 사용자 설정 (설계 / 미구현)

2026-10-24 사용자가 대기/완료 신고 화면을 제공했다. 신고의 처리 버튼을 선택한 뒤 전송해야
처리 완료가 되고, 이 동작과 별도로 게시글 글머리 이동이 필요하다고 설명했다.
사용자는 관리자가 신고 카테고리도 임의로 만들 수 있음을 추가 확인했다.

### 서로 다른 설정과 선택

- **신고 처리 카테고리/버튼:** 채널 관리자가 구성하는 신고 분류·처리 선택지다.
  화면에 보인 `광고`는 예시이며 이름/색/순서에 고정하지 않는다.
  **게시글 이동 대상 글머리**와 별도 설정으로 둔다. 이름이 같아도 같은 ID/조치라고 추정하지 않는다.
- 두 항목을 한 곳에 등록해 서로 자동 생성/변경하지 않는다. 신고 카테고리 추가/수정/삭제 자체는
  사이트 관리자가 수행하며 ArcaGuard는 허용된 읽기로 현재 목록을 확인·선택하도록 설계한다.
  이 요구는 사이트 카테고리 생성 API나 관리자 설정 변경 구현 승인이 아니다.
- 채널별로 `reportResolution.enabled`(기본 OFF), 선택한 신고 카테고리/처리 버튼의 검증된 식별값,
  최신 표시 이름/동작 검증 상태, 답변 문구, 작성자 결과 통지 설정(기본 OFF)을 분리해 저장한다.
  주제별 재설정은 채널 기본값 상속과 최종 적용값을 명시하고 다른 채널에 번지지 않게 한다.
- 사이트가 카테고리와 처리 버튼을 별도 필드로 제공하는지는 현재 직접 DOM 미검증이다.
  제공된 분류/선택지의 실제 관계를 확인해 각각 선택하고, 별도 필드가 없으면 존재한다고 만들어내지 않는다.
- 실제 목록에서 선택하며 CSS 선택자/임의 코드/엔드포인트를 사용자 설정으로 실행하지 않는다.
  안정적 식별값/효과를 확인할 수 없거나 동명 후보가 여러 개면 자동 제출을 보류한다.
  버튼 이름 변경/삭제/재생성/효과 변경 시 설정을 재검증하며 같은 색/첫 버튼/같은 이름으로 자동 대체하지 않는다.

### 답변과 결과 통지

- 사용자가 **카테고리·버튼에 지정한 문구를 사용**한다고 확인했다. 현재 설계는 선택한 사이트 프리셋의
  답변 문구를 함께 읽어 미리보기·선택하고, 사이트에서 문구를 수정한 뒤 다시 확인하는 방식이다.
  원하는 답변별로 사이트에서 처리 선택지를 구성할 수 있지만 그 생성/수정은 ArcaGuard가 자동 실행하지 않는다.
- ArcaGuard에 임의 답변 입력란을 제공하더라도 확인용 초안일 뿐 사이트 전송 문구를 바꾼다고 안내하지 않는다.
  현재는 신고별 자유 답변/템플릿 변수 치환을 전송 기능으로 제공하지 않는다. 미확인 답변 필드를 요청에 추가하거나
  원하는 답변을 보내려고 채널의 프리셋 설정을 자동 변경하지 않는다.
- 실제 프리셋 문구를 읽지 못하면 미확인으로 표시하고 자동 제출을 보류한다.
  예상 문구와 현재 문구가 달라지면 재선택/재검증하며 신고별 답변을 덮어쓰지 않는다.
  표시에는 일반 텍스트를 사용하고 스크립트/HTML/표현식을 실행하거나 신고자 원문/인증 정보를 삽입하지 않는다.
- `격리 완료` 같은 성공 문구는 실제 글 이동을 재조회해 확인한 작업에만 사용할 수 있다.
  Simulation/검토/글 이동 미확정 상태에서 완료 답변을 보내지 않는다.
- 화면의 `작성자 결과 통지`는 ArcaGuard 관리자용 결과 알림과 구별한다.
  별도 명시적 선택 없이는 작성자에게 통지하지 않으며, 그 설정을 바꿀 때 수신 대상/실제 효과를 표시한다.
  현재 사용자 요청은 설정 설계이며 작성자 통지나 실제 답변 전송을 수행한 것은 아니다.

### 처리 효과와 독립된 쓰기 경계

- 사용자 제공 화면에는 예상 조치의 `삭제`/`차단` 행이 있으며, 사용자는 현재 버튼 선택 시
  아무 내용도 표시되지 않는다고 확인했다. 이는 현재 예시의 사용자 확인일 뿐 모든 버튼이 무해하다는 보장은 아니다.
- 선택한 카테고리/버튼/채널마다 실제 효과를 검증한다. 삭제/차단 효과가 있거나
  효과가 미확인/미리보기 누락·변경이면 자동 제출하지 않는다. 이름이 `광고`라고 안전 판정하지 않는다.
  UI를 살펴보려고 전송/삭제/차단 버튼을 누르거나 미확인 요청을 추측하지 않는다.
- 신고 완료 제출은 게시글 이동과 별도의 관리자 쓰기 인터페이스/권한/배경 요청/결과 읽기를 가진다.
  기본 OFF와 Simulation, 정책 버전/긴급 중지/채널 검증을 적용하고 현재 화면의 버튼·전송을 자동 클릭하지 않는다.
  사용자 화면을 점유하지 않는 제출/결과 조회 경로가 없으면 수동 검토로 남긴다.

### 순서·부분 실패·다른 관리자

- 기본 자동 흐름은 OP-10 자격 및 공통 조건 → 게시글 이동 → 이동 결과 확인 →
  별도 활성화된 신고 처리 선택/답변 제출 → 신고 결과 재조회다. 처리 설정 OFF이면 신고 상태는 건드리지 않는다.
  사용자 수동 흐름이 신고 처리 먼저인 경우도 두 결과를 독립적으로 읽는다.
- 신고 상태(대기/완료·처리자·답변)와 글 이동 상태를 별도로 기록한다.
  신고 완료/답변 존재는 이동 성공 증거가 아니며, 격리 글머리만으로 우리 신고 답변 제출 성공을 주장하지 않는다.
- 글 이동 성공/신고 제출 실패는 부분 완료로 기록하고 글을 재이동하지 않는다.
  제출 시간 초과/불명확 응답이면 신고 상태/처리자/답변을 먼저 재조회하며 같은 답변을 무조건 다시 보내지 않는다.
- 다른 관리자가 완료한 신고에는 재전송/답변 덮어쓰기를 하지 않는다.
  신고만 완료됐고 실제 글은 미이동이면 `신고 완료 / 글 이동 미확인` 검토로 남기며,
  그 사실만으로 글의 처리가 끝났다거나 과거 신고를 새 자동 이동의 승인 근거라고 단정하지 않는다.
- 같은 글에 여러 신고 코드가 있으면 글 이동 작업과 신고별 처리 작업의 키를 분리한다.
  한 글을 여러 번 옮기지 않고 각 신고 제출은 현재 상태/설정/권한을 독립 확인한다.
- 신고 카테고리/버튼/그에 지정된 문구/작성자 통지/상속 설정 변경은 미전송 작업을 취소·재평가한다.
  설정 가져오기/복구로 신고 제출이나 작성자 통지를 켜지 않는다.
- 구현 책임: Phase 1 화면/필드/효과 조사, Phase 5 사용자 설정, Phase 7 별도 승인된 Mock/배경 쓰기 검증,
  Phase 9 부분 실패·복수 관리자 회귀. 현재는 조사/설계만 하며 실제 제출·이동은 실행하지 않는다.
