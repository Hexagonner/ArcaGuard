- 상세 주소 형태는 `/reports/b/{channel}/{reportId}`로 제공됐다. reportId는 불투명 식별자로 취급하며
  대상 articleId/작성자/인증 값과 혼동하거나 숫자로 강제 변환하지 않는다.
- 신고자 프로필 링크에 닉네임/번호 형태가 제공됐다. 해당 번호의 불변성/고유성은 추가 검증 전이다.
- 사용자가 조회하기 상세 화면에 **신고 내용/사유가 표시됨**을 확인했다.
  실제 사유 문자열은 요청/저장하지 않았으므로 이번 신고의 `광고` 일치 여부는 미확인이다.
- 고유 계정 키, 신고 페이지 완전성/철회/중복 행/댓글 신고, DOM 선택자, 조회 권한의 채널별 의미는 미검증이다.
- 익명화된 계약 예시는 `tests/fixtures/arcalive/report-row.user-provided.json`이다.
  모든 계정/ID/링크/시각 값은 합성이고 HTML 캡처가 아니다. 실제 DOM/수집기 검증으로 사용하지 않는다.

## USR-REPORT-02 — 아카라이브 신고 알림과 상세 원문 필드

출처: 사용자가 제공한 알림 스크린샷 및 별도 테스트 신고 상세 표 (2026-10-24).
근거는 `user-provided`이며 에이전트가 신고 URL을 직접 열거나 알림을 누른 것은 아니다.
기존 USR-REPORT-01과 같은 신고라고 가정하지 않는다. 실제 계정명/개별 신고·게시글 ID/원문 사유는 저장하지 않는다.

- 사이트 고유 알림의 새 신고 메시지와 읽지 않음 표시가 화면에 보인다. 사용자는 관리자 선택으로
  신고 알림을 받을 수 있고 알림을 누르면 해당 신고 상세 화면으로 들어간다고 설명했다.
- 상세 필드: 신고 코드 / 신고 채널 / 신고 유형 / 대상 / 작성자명 / 최초 신고 시각 /
  총 신고된 횟수 / 신고 사유 / 처리 상태 / 조치.
- 제공된 예시의 유형은 `ARTICLE`이고 대상은 글 링크다. 작성자명은 신고자 필드가 아니다.
  신고 사유 영역에는 신고자 프로필 링크와 해당 사용자의 사유가 짝으로 표시된다.
- 제공된 사유 문자열에는 `광고`가 포함된다. 이는 사용자 제공 텍스트의 문자열 관찰이지
  구현된 수집기/OCR/광고 탐지 엔진의 테스트 결과는 아니다.
- 총 신고된 횟수 표시는 `1번`이다. 이 숫자를 고유 신고자 수로 사용하지 않는다.
  여러 사유 행/중복 신고/수정·철회/집계 묶음의 의미는 미검증이다.
- 앞서 제공된 신고자와 동일한 프로필 주소가 다른 표시 이름 형식으로 나타났다.
  이름의 `#번호` 표시 유무만으로 계정이 다르다고 판단하지 않는다. 프로필 식별자의 불변성도 아직 미검증이다.
- `처리 상태: 대기`, `조치` 표제는 확인되지만 조치 버튼/HTTP 방식/삭제·이동 의미/
  실행 권한은 확인되지 않았다. `조치` 표제만으로 자동 변경 기능을 구현하지 않는다.
- 알림 DOM/전달 방식/페이징/보관 범위, 상세 읽기나 알림 접근의 읽음 처리 부작용은 미검증이다.
  알림 자동 클릭/모두 읽기/처리 상태 변경은 수행하지 않았다.
- 익명 계약: `tests/fixtures/arcalive/report-detail.user-provided.json`.
  신고 사유도 가상 문구로 교체했으며 실제 HTML Fixture나 관리 조치 구현이 아니다.

## USR-REPORT-03 — 사이트 자체 1회 제한과 총 신고 수 사용

- 2026-10-24 사용자가 신고는 한 번만 가능하고 받은 신고 수도 확인된다고 설명했다.
  동일 계정/대상에 대한 사이트 제한을 사용한다는 현재 계약으로 반영한다. 출처는 `user-confirmed`다.
- 이전의 로컬 고유 신고자 집계/번호 불변성 필수 계획을 대체한다. 사이트 총 신고 수를 사용하고
  안정적 계정 키 부재만으로 수를 거부하지 않는다. 별도 신고자 기여 키/장부는 만들지 않는다.
- 신고자 이름/사유 출처 확인은 유지하고, 재조회 시 최신 값으로 교체한다.
  알림 수를 신고 수에 더하거나 같은 작업을 반복 실행하는 것은 별도로 방지한다.
- 사이트의 실제 요청/수신 프로토콜/읽음 부작용/현재 DOM을 에이전트가 검증한 것은 아니다.
  아카라이브를 직접 요청하지 않고 비동기 읽기의 일반 원리만
  [MDN Fetch 문서](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)에서 확인했다.
- 같은 origin의 비동기 요청은 일반적으로 페이지 이동 없이 응답을 읽고 브라우저가 기존 세션을 처리한다.
  사이트 자체 정책/권한/부작용 검증과 무거운 처리의 분할이 추가로 필요하므로 무방해 지원 완료로 보고하지 않는다.
