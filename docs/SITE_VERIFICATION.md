## TOOL-01 — 기존 사이트 접근 실패 원문 재확인

2026-10-24 같은 대화의 기존 브라우저 실패 기록을 다시 읽었다. 차단 대상에 재접속한 것은 아니다.

- 원문: `The site-safety policy blocks this action; no user permission prompt or Auto-review was attempted.`
- https://arca.live의 site-safety 단계에서 관측 권한을 얻지 못했다는 도구 응답이다.
  일반 연결 실패/로그인 실패/채널 관리자 권한 부족으로 재분류할 근거는 없다.
- 사용자가 브라우저 관리의 차단 목록에 해당 사이트가 없음을 확인했다. 출처는 사용자 진술이다.
  사용자 차단 목록과 같은 것이라고 단정하거나 삭제할 항목이 있다고 안내하지 않는다.
- 내부 차단 규칙/오탐 여부/정책 변경 가능 여부는 응답에 나타나지 않아 미확인이다.
  사용자 승인창이나 Auto-review 거절을 해소하면 해결된다고 설명하지 않는다.
- 실제 Chrome localhost UI 접근 성공과 사이트별 접근 거절은 별도로 기록한다.
  이후 다른 도구/브라우저/원시 요청/프록시로 차단된 관측을 대신 수행하지 않았다.
- 지원 진단이 필요한 외부 제약으로 남긴다. 사용자에게 문제 신고 방법은 안내했지만
  피드백/지원 요청을 실제 제출하거나 차단 해제를 수행한 것은 아니다.

## Phase 1 마무리에 필요한 근거와 후속 단계 경계

2026-10-24 재점검. 이미 제공된 신고 열/상세 사유/총수/1회 제한/수동 수정 순서는 다시 요구하지 않는다.

- **신고 읽기:** 목록 필터/이전 내역 조회 화면은 USR-REPORT-06으로 확보했다.
  실제 링크/페이지 범위/이전 내역 누락·중복/목록과 상세의 대응을 검증해야 하며 보이는 네 행으로 완전성을 추정하지 않는다.
- **읽음 부작용:** 사용자는 알림을 직접 눌러야 읽음 처리된다고 답했다(USR-REPORT-05).
  직접 열기와 비동기 읽기의 부작용이 같다고 추정하지 않는다. 안전한 배경 읽기 검증은 별도로 필요하다.
  알림을 클릭하지 않고 신고 목록을 읽는 경로도 독립적으로 권한/부작용을 확인해야 한다.
- **격리 대상:** 사용자가 TEST 생성/관리자 전용 설정 완료를 답했다(USR-CATEGORY-02).
  설정 완료의 출처는 사용자 확인이며 현재 목록 ID/실제 접근 제한/본문 보존/현재 상태는 직접 검증 전이다.
- **현재 사이트 구조:** 게시글/댓글 경계, 현재 분류·기처리 상태, 이미지 앵커 href와 파일 주소의 관계는
  참고 코드만 있고 직접 DOM 근거가 없다. 새로운 도구나 임의 선택자로 이 공백을 채우지 않는다.
- **무방해 경로의 조사 범위:** 수정 화면에서 글머리 선택이 가능하다는 사용자 설명은 확보했다.
  읽기 전용으로 확인 가능한 권한/필드 범위/변경 의미와 아직 확인할 수 없는 요청·경합 조건을 구분한다.
  실제 이동을 보내거나 숨겨진 인증 필드/비밀값을 수집하는 작업은 Phase 1 완료 조건으로 요구하지 않는다.
- 현재 브라우저 도구의 사이트 정책 차단으로 직접 DOM/권한/요청 근거는 확보하지 못했다.
  사용자 답변은 `user-provided`로 보완하되 직접 검증으로 바꾸지 않는다. 차단 대상 재시도/우회는 하지 않는다.
- **후속 검증:** 실제 한 글 이동/전후 결과/동시 편집 보호/화면 보존은 Phase 7,
  모델 설치·한국어 성능/AI 판정 기준은 Phase 8, 전체 통합·부하·복수 관리자 회귀는 Phase 9다.
  이 실행 검증을 하지 않았다는 이유만으로 Phase 1에 쓰기나 AI 구현을 끼워 넣지 않는다.
- 지금 신고 임계값 N을 확정하거나 광고 사례를 더 모으는 것은 조사 완료의 선행 조건이 아니다.
  두 정책/실패 시 처리 계약은 OP-10에 설계됐으며 구현 단계에서 사용자 설정을 지원한다.

  실제 존재하는 DOM 영역의 변경을 관측한다. 닫힌 알림 패널에 아직 없는 상세 링크까지 만들어 주는 API는 아니다.
- 현재 코드: `src/main.js`는 자체 UI와 메뉴 어댑터만 연결한다. `src/adapters/arcalive`에는 규칙 문서만 있고
  신고/본문/편집 수집기는 없다. `vite.config.js`의 match/document-idle 설정은 실행 대상 설정이며 관리자 DOM 검증이 아니다.
- 기존 실험 재검토: PLATFORM-03의 3경로/양성 대조 1건/700ms별 관측과 화면 상태 보존은 JSON에 기록돼 있다.
  localhost 합성 HTML 읽기이며 실제 사이트 선택자·권한·CSP·알림 구조나 모든 입력의 안전을 입증하지 않는다.
- **판정: Userscript의 일반 DOM 접근은 지원됨 / 도구의 현재 사이트 관측은 제한됨 / 운영에 사용할 실제 DOM은 미검증.**

### CHECK-02 — 백그라운드 신고 알림 수신

- 사용자 자료는 신고 알림과 상세 링크가 존재함을 보여 준다. 패널을 열지 않아도 링크가 DOM에 있는지,
  어떤 신호가 신규 신고를 뜻하는지, 누락·재연결·정지 후 얼마나 복구되는지는 검증하지 못했다.
- [GM_notification 문서](https://www.tampermonkey.net/documentation.php?q=GM_notification)의 API는 알림 표시용이다.
  사이트 신고 알림 또는 다른 애플리케이션 알림을 자동 구독하는 기능으로 취급하지 않는다.
- 고정 커밋의 [WebSocket.jsx](https://github.com/lekakid/ArcaRefresher/blob/1b22bbf1939f03629f514362a75697ffa25336c4/src/core/WebSocket/WebSocket.jsx)
  (blob `5587ee64183779ba0736b02efcb19e8f4e0d5b15`)를 다시 읽었다. 원본 소켓 교체/메시지 수정·억제 코드이며
  이 파일 자체에는 신고 알림 전용 타입/필드 계약이 없다. 실제 신고 수신 지원으로 해석하거나 그대로 설치하지 않는다.
  파일명 검색/이 두 파일 검토만으로 저장소 전체에 관련 코드가 전혀 없다고 주장하지 않는다.
- **판정: 현재 수신기 미구현 / 실제 수신 경로 미검증.** 허용된 실제 신호 또는 부작용 없는 목록 대조가 검증돼야 한다.
  알림 아이콘/패널 자동 클릭이나 읽음 처리로 이를 대신하지 않는다.

### CHECK-03 — 광고 판단 후 백그라운드 글머리 이동

- [MDN Fetch 사용 문서](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)는 비동기 요청과
  POST/FormData·URLSearchParams, 동일 출처의 기본 인증 포함 동작을 설명한다. 로그인 자료를 읽어 저장할 필요가 있다는 뜻은 아니다.
  [Window.fetch](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch)는 CSP connect-src 적용을 명시한다.
  따라서 화면 전환 없는 요청은 일반 기술로 구성할 수 있지만 특정 사이트의 저장 허용/성공을 보장하지 않는다.
- 참고 [http.jsx](https://github.com/lekakid/ArcaRefresher/blob/1b22bbf1939f03629f514362a75697ffa25336c4/src/func/http.jsx)
  (blob `d9513ef1a18f73b082bc3aff9d6867953e0a00ac`)의 범용 GM 요청/HTML 해석을 재대조했다.
  검증된 글머리 변경 요청/권한/서버 필드 보존의 근거는 아니며 사용 권한을 추가하지 않았다.
- 현재 탐지/AI/정책 실행/이동 어댑터는 없다. OP-10의 두 정책은 설계 상태이며 모델의 한국어 판정 성능도 미검증이다.
  TEST 식별값·실제 격리 효과·저장 의미·본문/기타 필드 보존과 결과 읽기가 필요하다. HTTP 성공만으로 이동 성공을 기록하지 않는다.
- **판정: 브라우저 기술상 조건부 구현 가능 / ArcaGuard 이동 미구현 / 실사이트 배경 이동 성공 미검증.**
  DOM과 정상 저장 동작이 확인되고 별도 지정 글 쓰기 승인이 있어야 실제 전후 검증을 할 수 있다.

### CHECK-04 — 설정에 따른 선택적 신고 완료

- 사용자 화면의 실제 동선은 사용자 지정 처리 버튼 선택 → 전송 → 처리 상태 확인이다.
  별도의 고정된 ‘처리 완료’ 버튼/필드/요청이 있다고 만들지 않는다. 글머리 이동과 독립인 OP-11을 따른다.
- **판정: 선택 분기는 설계 가능 / 제출 기능 미구현 / 안전한 배경 제출 및 결과 미검증.**
  OFF면 제출/작성자 통지를 보내지 않고 이동 결과만 기록한다. ON이면 이동 결과를 먼저 확인한 뒤
  검증된 분류·프리셋 답변·효과·권한으로 별도 제출하고 신고 상태/답변/처리자를 재조회해야 한다.
  이동 성공/신고 실패는 부분 완료로 남기고 재이동하거나 타 관리자 답변을 덮어쓰지 않는다.
- 삭제/차단 칸 공란만으로 부작용 없음을 확정하지 않는다. 자동으로 보이는 처리 버튼을 누르는 대안도 채택하지 않는다.
  UI를 움직이지 않는 허용된 제출 경로가 없으면 자동 신고 완료는 보류한다.

### 실행 한계와 검증을 끝내는 조건

- [Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)을 2026-10-25 재조회했다.
  hidden과 frozen/discarded는 다르며 정지·폐기된 페이지는 타이머/fetch 콜백 또는 모든 JS 실행이 제한된다.
  Chrome이 켜져 있어도 실행 가능한 사이트 페이지/Userscript 없이 상시 수신·조치를 보장하지 않는다.
- 도구의 사이트 관측 제한은 제품의 DOM 접근 불가능을 증명하지 않는다. 반대로 일반 API 지원은 제품의 실사이트 성공이 아니다.
  실제 권한/필드·ID/조회 범위/알림 경로와 부작용/정상 저장·제출 의미의 허용된 읽기 검증이 선행돼야 한다.
- 이후 Phase 7의 별도 지정 테스트 글 승인과 검증된 UI가 갖춰지면 이동 전후 글머리/본문/접근 제한을 대조한다.
  신고 제출 OFF/ON 및 전후 상태, 글 이동과 독립인 부분 실패, 화면·초안·IME 보존도 검증해야 한다.
  현재는 승인/실사이트 근거가 없는 쓰기를 보내거나 이 조건을 통과한 것으로 보고하지 않는다.

## PLATFORM-04 — 핵심 흐름의 실행 가능한 독립 실험

2026-10-25 사용자 요청에 따라 일반 브라우저 기술의 실현 가능성을 실제 HTTP 왕복과 서버 상태 변경으로 시험했다.
대상은 `http://127.0.0.1:5185/` 고정 합성 서버이며 아카라이브의 DOM/요청을 모사해 검증된 것으로 제시하지 않는다.

- 도구: 기존 Node와 실제 Chrome/157. 새 의존성/확장/권한 grant는 없다.
  개발 전용 `scripts/serve-workflow-lab.js`, `tests/manual/workflow-lab.html`, `workflowLab.js`는 배포물에 포함하지 않는다.
  루프백 Host/Origin/경로/요청 크기/실행 수를 제한하고 CSP는 연결을 self로 한정했다. 프록시나 외부 요청 경로가 없다.
- 흐름: 로컬 SSE 알림 → 합성 신고 HTML 읽기/대상·총수·사유 확인 → 합성 신고 기준 조건 → 현재 글 JSON 읽기 →
  백그라운드 POST → 글머리/본문 재조회 → 선택적으로 별도 신고 POST → 신고 상태/지정 답변 재조회.
  알림 패널/관리 폼 클릭, 화면 이동/새로고침은 처리 경로에 없다. 대조 탭 열기는 실험자가 실행 전 별도로 수행한 동작이다.
- 결과: 현재 코드의 최종 기준 실행 **8/8**, 대조 탭 관측을 동반한 별도 실행 **8/8** 통과.
  서버가 기록한 요청 횟수/상태 변화/순서와 클라이언트의 최종 상태를 대조했다.
  1. 신고 완료 OFF: 이동 1회, 신고 전송 0회, 신고 대기 유지.
  2. ON: 이동/재조회 뒤 신고 완료 1회와 지정 답변 재조회.
  3. 중복 알림 3회: 처리 중복 억제로 이동/신고 전송 각각 1회.
  4. 이미 격리된 글: 이동/신고 전송 0회.
  5. 이동 403: 이동 미성공, 신고 전송 0회, held.
  6. HTTP 200이나 실제 글머리 미변경: 재조회로 실패 판정, 신고 전송 0회, held.
  7. 이동 성공/신고 전송 503: 글머리는 격리, 신고는 대기, partial, 재이동 없음.
  8. 신고 수 미달: 이동/신고 전송 0회.
- 각 처리 구간의 URL/방문 기록 길이/스크롤/activeElement/초안/선택 범위가 보존됐고
  수집한 focusin/scroll 이벤트에서도 기준과 다른 상태를 찾지 못했다. 전 구간 입력 지연/IME/짧은 모든 상태 변화를 측정한 것은 아니다.
- 대조 탭에서는 처리 시작 전부터 완료 뒤까지 입력한 합성 초안/커서/포커스/스크롤을 대조해 동일함을 확인했다.
  **알림 수신 시 처리 탭 자체 기록은 visible/hasFocus true였으며 hidden 조건을 관측하지 못했다.**
  따라서 ‘다른 탭을 열었으니 숨김 탭 실행 성공’으로 판단하지 않는다. companionTrial.hiddenConditionMet는 false다.
  대조 중 키 입력을 계속하거나 실제 IME 조합/탭 정지·폐기·절전에서 시험한 것도 아니다.
- 초기 대조 시도에서 이전 결과가 남을 수 있어 새 실행 시작 시 원시 결과를 지우도록 수정했다.
  최종 파일은 수정 후 별도 실행 결과다. 처음의 대기 도구 timeout은 이후 완료 상태를 직접 확인했으며 서버 처리 실패로 세지 않는다.
  제한된 읽기 평가 환경의 document.hasFocus 미지원은 페이지 실행 결과 JSON으로 대체했으며 브라우저 정책을 바꾸지 않았다.
- 증거: `tests/manual/workflow-lab.chrome.visible.json`, `workflow-lab.chrome.companion.json`, `workflow-lab.chrome.png`.
  최종 전체 결과 화면을 직접 확인했다. JSON 구조/8개 통과/서버 상태/대조 관측 시간 범위·보존/hidden 미충족도 재검사했다.
  실험용 탭 2개와 서버는 저장 후 종료했다.
- **입증 범위:** 합성 서버가 제공하는 신호·읽기·저장·결과 경로가 있을 때 위 비동기 흐름과 실패 분기는 구현 가능하다.
  **미입증:** 실제 아카라이브 DOM/알림 프로토콜/권한/저장·신고 제출 의미/본문 보존·격리 효과,
  Tampermonkey sandbox 안의 실제 실행, 숨김·정지된 탭 실행, 광고 분류/AI 품질, 다중 관리자 경합.
  합성 서버의 revision 조건 지원을 실제 사이트의 조건부 변경/잠금 지원으로 취급하지 않는다.
  이 개발 서버는 최종 사용자 필수 서비스가 아니며 운영 감시/이동 기능을 구현하거나 Phase 1 완료로 선언한 것이 아니다.
